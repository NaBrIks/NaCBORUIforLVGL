# Рабочий вариант: привязки к полям входящих сообщений

Дата: 2026-10-20.
Статус: рабочий вариант развития, поддержанный владельцем для дальнейшего обсуждения. Не окончательный контракт и не реализованная возможность.

Продолжение обсуждения зафиксировано в [рабочей модели реестра и привязок](../readme_bindings.ru.md). В ней описаны извлечение по спросу, зависимости, постоянные и экранные подписки, первоначальное `--` и возврат на экран. Пример прямой привязки ниже остаётся иллюстрацией исходной идеи, а не окончательным выбором структуры.

## Назначение

Первый самостоятельный результат библиотеки — создание дерева LVGL, назначение свойств и стилей из описания вместо большого количества ручных setter-вызовов. Привязки рассматриваются как дополнительный механизм поверх этого загрузчика; прямое управление элементами из кода остаётся возможным.

Предлагаемый механизм привязок — стандартизированная обработка сообщений из заданного приложением потока или очереди. Основной рассматриваемый payload — CBOR; JSON обсуждается как альтернативный формат входящих данных. Не предполагается, что очередь сама понимает CBOR: транспорт доставляет сообщение, а адаптер и декодер предоставляют его обработчику привязок.

## Два разных вида документов

- Описание интерфейса задаёт дерево, стили и правила привязок; загружается при создании или замене экрана.
- Сообщения с данными поступают при обновлении источников; из них извлекаются значения для уже созданных элементов.

Поддержка JSON-сообщений не означает автоматически поддержку загрузки UI из JSON на устройстве. Это отдельный вопрос.

```text
Заданная очередь / поток событий приложения
  -> адаптер доставки (источник, формат, буфер и длина)
  -> декодер CBOR, либо опциональный декодер JSON
  -> выбор подходящих привязок и извлечение полей
  -> форматирование / согласованное преобразование
  -> обновление объектов в контексте LVGL
```

Общий обработчик должен использовать одинаковую семантику привязок для поддерживаемого подмножества CBOR и JSON. Их типы не полностью совпадают; допустимые типы и преобразования ещё нужно определить. Промежуточное JSON/DOM-дерево и конвертация каждого CBOR-пакета в JSON не являются обязательными.

## Именованный реестр приложения

Для МК рассматривается фиксированный, ограниченный набор предоставленных приложением возможностей. Реестр может быть статической таблицей в прошивке. Имена — символьные UTF-8, без перекодировки в числовые ID.

Возможные виды записей: читаемое текущее значение, записываемое значение или действие, источник сообщений. Данные массивов и идентичность конкретного устройства внутри сообщения не обязательно требуют отдельной регистрации каждого элемента.

Приложение знает, как получать данные и выполнять действия; описание экрана выбирает источник, поле и назначение. Для входящего сообщения не требуется автоматически создавать Subject на каждое поле или постоянно хранить полную копию всех данных в библиотеке.

## Иллюстрация, не утверждённая схема

Сообщение источника `tpms`, показанное в JSON для читаемости:

```json
{
  "sensor": "frontLeft",
  "pressure_Psi": 32.5,
  "temperature_C": 24.0,
  "battery": 87
}
```

Условное описание элемента:

```json
{
  "type": "label",
  "id": "frontLeftPressure",
  "binding": {
    "source": "tpms",
    "where": { "sensor": "frontLeft" },
    "field": "pressure_Psi",
    "target": "text",
    "format": "%.1f psi"
  }
}
```

Смысл: из сообщений источника `tpms` выбирать сообщения переднего левого датчика, извлекать `pressure_Psi`, форматировать и обновлять текст указанной надписи. `source` обозначает логический источник; отдельная физическая очередь на каждый источник не требуется. Все имена ключей и структура примера остаются предметом обсуждения; универсальный язык фильтров/выражений пока не выбран.

## Время жизни и первоначальное значение

Визуальная привязка ограничена временем жизни целевого элемента; обработка источника и запись значения в реестр могут быть постоянными и продолжаться без этого экрана. Входящее сообщение может быть краткоживущим. Перед отложенной обработкой необходимо обеспечить владение буфером либо скопировать извлечённые значения. После применения обновления сообщение можно освободить, если от него больше ничего не зависит.

Уточнение владельца: при включении до получения значения отображается `--`. При возврате на экран постоянная подписка позволяет взять последнее известное значение реестра; если обработка была отключена и актуального состояния нет, нужно ждать нового события с `--`. Чтение текущего состояния приложения также возможно. Сроки актуальности и политика скрытых сохранённых экранов ещё открыты. Кэш или Subject — возможные инструменты, не обязательная часть каждой привязки.

Нельзя предполагать, что несколько получателей обычной очереди получают один и тот же пакет: для рассылки нужны соответствующие гарантии транспорта или диспетчер подписчиков.

## Открытые вопросы

- Интерфейс адаптера очереди/потока, подписка и удаление подписок при выгрузке экрана.
- Типы, вложенные пути, массивы, идентификация источника и простые условия отбора.
- Отсутствующее поле, неверный тип, неизвестное имя и повреждённое сообщение: явные правила вместо молчаливой подстановки нуля.
- Ограничения размера и вложенности, количество привязок, стоимость обработки и политика при переполнении очереди.
- Порядок обновлений, владение данными и синхронизация с задачей LVGL.
- Форматирование, разрешённые преобразования и граница со сложной логикой приложения.
- Обратное направление: запись значений и вызов именованных действий по событиям интерфейса.

## Основание в существующем эксперименте

В `../ESP32-BLETPMS-and-more` при анализе исходников 2026-10-20 найдены:

- `src/modules/wifi/wifi.cpp`: создание CBOR с полями `cbor` / `IP` и отправка в `CBOR_loop`.
- `src/modules/lcd/Network/lvgl_network.cpp`: приём пакета, извлечение `IP`, отложенное обновление надписи.
- `src/modules/web/web.cpp`: другой обработчик того же потока пересылает CBOR в WebSocket.
- `src/modules/lcd/TPMS/lvgl_tpms.cpp`: получение типизированного TPMS-события, локальное создание CBOR и ручное сопоставление полей двум надписям.

Это исходный пример направления, не проверенная реализация нового механизма. В ходе обсуждения сборка и аппаратные испытания не выполнялись; соседний проект не изменялся.
