# Каталог данных, динамические источники и история

Статус 2026-11-07: первый вариант реализован по поручению владельца. Текущее API —
[руководство](../readme_data_catalog_ru.md), принятое решение —
[ADR](../adr/ADR_20261107_data-catalog-history.md). Ниже сохранён исходный анализ;
предложения о дальнейших расширениях не означают их реализации.

Дата анализа: 2026-11-07. Статус: **предложение, не реализованный контракт**.
Документ сопоставляет пожелания владельца с текущим кодом. Он не разрешает
переписывание ядра, не меняет binding ABI и не утверждает аппаратную приёмку.

Рекомендация: развивать существующий `DataRegistry`. Уже есть единый каталог
типов и доступных действий, хранилище последних значений и привязки страниц.
Нужны более содержательные описания, явное изменение каталога и необязательная
история с ограниченной памятью. Полный новый движок биндингов для этого не нужен.

## Что уже работает

| Требование | Фактическое состояние |
| --- | --- |
| Общие данные для всех страниц | Приложение владеет одним `DataRegistry`; экземпляры страниц владеют своими подписками и событиями. |
| Скаляр, структура и массив | `DataSchema` описывает типы, поля, границы числа, текста и массива; необъявленные поля отвергаются. |
| Описание и значение вместе | `DataSource` содержит имя, схему, необязательный setter и `title`; реестр хранит committed/pending снимки этого источника. |
| Единый каталог для UI/MCP | `catalog_json()` выводит те же зарегистрированные схемы, writable и actions; каталог входит в `capabilities.binding`. |
| Первая отрисовка и возврат | Последний снимок хранится независимо от страницы. При возобновлении страница заново подписывается и обновляет значения. |
| Команды приложения | Действия и запись вызывают зарегистрированные обработчики; UI не меняет измерения произвольным внешним publish. |
| История Windows | Пример сам хранит 32 отсчёта CPU/RAM/GPU и передаёт их как обычные данные; универсальной истории/усреднения в ядре нет. |

Источники фактов: [описания и API реестра](../../include/lvgl_cbor/data_registry.hpp),
[хранение, регистрация, публикация и экспорт](../../src/data_registry.cpp),
[жизненный цикл привязок](../../src/screen_bindings.cpp),
[Windows SystemMetrics](../../examples/windows_player/src/system_metrics.cpp),
[руководство биндингов](../readme_bindings_ru.md).

`publish()` ставит полную замену снимка; `flush()` коммитит пакет до уведомления
наблюдателей. Несколько публикаций одного источника до flush сворачиваются в
последнюю. Это удобное хранилище актуального состояния, но не журнал всех
измерений. Повтор того же числа не увеличивает ревизию значения и не вызывает
наблюдателя — это отдельно проверено [native-тестами](../../tests/native/bindings.cpp).

## Свободный дизайн через CBOR: граница обещания

Разметка, стили, композиция страниц, навигация, привязки и события задаются
документом проекта. Агент может собрать новый экран без перестройки прикладной
логики, используя фактически объявленные компоненты, методы, ресурсы и данные.

CBOR не добавляет новый исполняемый код. Нативные draw-обработчики, драйверы,
необъявленные ресурсы и новые операции должны быть зарегистрированы приложением.
Например, полностью изменить внутреннюю геометрию нативного спидометра можно
только в пределах его опубликованных параметров/методов либо после расширения
самого компонента. Произвольного языка рисования в текущем runtime нет.
Это не препятствует свободному построению страниц из существующих компонентов.

## Одна понятная модель данных

Предлагается сохранить три обязанности: описание источника, последний снимок и
привязку виджета. Все данные, включая системные и производные, видны через один
реестр. Отдельного списка «специальных системных биндингов» не нужно.

```mermaid
flowchart LR
    P["Адаптер приложения: id, значение, время, качество"] --> R["DataRegistry: последние сырые и производные снимки"]
    P --> H["Необязательно: ограниченная история и фильтр"]
    H --> R
    R --> B["Привязки экземпляров страниц"] --> V["Методы LVGL-компонентов"]
```

На схеме один экземпляр реестра. Обработчик истории получает нормализованные
отсчёты от адаптера до их сворачивания в latest snapshot и публикует обычный
производный источник в тот же реестр. Циклической зависимости и универсального
графа вычислений здесь нет. Задачи транспорта передают принадлежащие приложению
данные в сериализованный контекст; сам реестр не создаёт потоки.

Для простого периодического графика допустимо брать последний снимок по
таймеру. Но тогда график показывает последнее доступное значение на момент
таймера, а не каждый входной пакет. Для среднего/min/max за период обработчику
должны достаться все учитываемые входные отсчёты; свернувшийся mailbox их уже
не восстановит. Частота UI и частота сбора могут отличаться.

### Описания источников

Оставить символическое стабильное имя, тип и права записи. Расширить текущий
descriptor ограниченными полями `title`, `description`, `unit` и описаниями полей
структуры. При необходимости добавить подписи перечислений и сведения о
периоде/свежести. Это один источник для проверки значений, редактора и MCP,
а не три параллельные схемы. Внешнее отображаемое имя можно переименовать;
идентичность источника от этого не меняется.

Метаданные периода объясняют агенту данные, но сами по себе не запускают таймер.
Флаг writable не делает измерение настройкой: setter и action по-прежнему
явно предоставляет прикладной код. Системные время, сеть и память объявляются
теми же средствами в своих адаптерах.

### Фиксированный код и настоящая статика

Для фиксированных источников удобна таблица объявлений рядом с кодом поставщика.
Сейчас `add_source` принимает owned-описание и рекурсивно копирует схему.
`std::map`, `std::string` и `shared_ptr` занимают RAM и при объявлении переменной
со словом `static`. Нельзя обещать хранение во Flash, просто вынеся код
регистрации в глобальную переменную.

Первый этап может сохранить нынешнее owned-хранение и убрать повторное ручное
описание данных в других слоях. Следующая возможная оптимизация — неизменяемые
POD/constexpr descriptors с массивами полей и строковыми литералами, представляемые
реестру как read-only view. Их lifetime должен быть не меньше lifetime реестра;
динамические описания должны оставаться owned. Это отдельная работа после
измерения, а не обязательное условие предлагаемого каталога.

## Динамические датчики и настройки

Текущий API умеет добавить источник в UI-контексте, но не умеет удалить или
заменить его описание. Изменение каталога не имеет отдельной ревизии.
В S3 capabilities кешируется и сейчас обновляется по ревизии каталога виджетов;
одно добавление DataSource не инициирует обновление этого снимка:
[интеграция приложения](../../examples/s3_style_lab/main/main.cpp).

Предлагается:

1. Добавлять динамические источники в тот же реестр с устойчивой идентичностью
   из настройки датчика. Использовать имя/ID сущности, не её позицию в списке.
2. Временно отключённый датчик сохраняет описание; показания становятся
   unknown/stale, доступность объясняется явно. Это позволяет заранее оформить
   экран и не превращать краткий обрыв связи в удаление всех привязок.
3. Настоящее удаление источника, смену его типа и освобождение описания выполнять
   по определённому жизненному циклу, в том же UI-контексте. Нельзя незаметно
   переиспользовать старый ID для другого датчика. На первом этапе при редкой
   смене структуры допустима согласованная пересборка проекта вместо сложного
   ремонта всех живых зависимостей.
4. Ввести отдельную ревизию каталога, условно `catalogRevision`: она меняется
   при изменении описаний/состава, а не при каждом показании. По ней обновлять
   существующий capabilities snapshot и уведомлять клиентов через имеющийся WS.
   Имя и форма уведомления ещё требуют выбора; смена каталога не равна изменению
   сохранённого UI-проекта.

В нынешних путях массив адресуется индексом. После удаления и уплотнения списка
`[2,"temperature"]` может обозначать другой датчик. Поиска элемента массива по
ID и автоматического создания строк сейчас нет. Для небольшого числа датчиков
проще отдельные устойчивые имена; для фиксированного массива допустимы стабильные
слоты без уплотнения и явный ID. Не следует обещать сотни отдельных источников:
сегодня контракт ограничивает их число 32, изменение потолка требует проверки
памяти. Поддержка адресации коллекций по ключу — отдельное дальнейшее решение.

## История и простая обработка

История принадлежит данным/приложению, а не графику. Уход со страницы может
приостанавливать её биндинги, но не нужное приложению накопление. При возвращении
график получает уже существующую историю. Спрос UI можно использовать для
дорогого форматирования/экспорта, но не для остановки сигнализации или истории,
которая должна продолжаться без открытого экрана.

Для каждой включённой серии задать заранее ёмкость, период и поведение при
пропуске. Использовать монотонное время; NTP/перевод часов не должны сжимать или
растягивать уже записанный график. Для равномерного ряда достаточно времени
начала, периода, количества заполненных точек и признаков пропусков; отдельный
timestamp нужен только там, где нерегулярность действительно важна.

Отсутствующий/устаревший отсчёт — разрыв, а не ноль. Первое значение не заполняет
всю прошлую историю. Период без валидных входных отсчётов остаётся пустым;
перенос последнего значения допустим только как явно выбранная политика с
контролем возраста. Числовое значение `-1` не является универсальным маркером
пропуска: оно может быть настоящим измерением. Нужна отдельная валидность,
преобразуемая в представление конкретного графика на границе компонента.

Минимальные необязательные операции:

| Операция | Для чего и как ограничивается |
| --- | --- |
| Последнее за период | Равномерный график с постоянной ёмкостью; одинаковое значение всё равно даёт отсчёт времени. |
| Среднее за период | `sum/count` в текущем интервале; среднее считается по определённым входным отсчётам, а не по перерисовкам. |
| Скользящее среднее SMA | Только при необходимости: фиксированное окно валидных отсчётов/периодов и заранее известная память кольца. |
| Экспоненциальный фильтр EMA | Одно состояние и параметр сглаживания; при нерегулярных входах учитывать elapsed time. Реакцию на длинный разрыв определить явно. |
| Min/max за период | Сохраняет краткие выбросы, которые скрыло бы среднее; две границы можно показать отдельными сериями, если компонент это умеет. |

Для первой реализации достаточно записи последнего значения и одного выбранного
агрегатора. SMA/EMA/min/max не обязаны включаться для каждого источника.
Результат обработчика — обычный типизированный источник; дополнительных методов
«биндинга на среднее» или отдельного протокола графиков не требуется. UI должен
видеть семантику серии и единицы через каталог, а не угадывать их по имени.

## Память и выключение модулей

Текущие [лимиты binding-контракта](../../include/lvgl_cbor/binding_contract.hpp):
32 источника и 32 действия, 16 полей структуры, глубина схемы 4, до 256 элементов
массива, до 16 KiB на CBOR-значение и до 64 KiB на совокупные committed/pending
значения в их CBOR-представлении. Это ограничения wire-данных, **не лимит heap**.

Ограничения разных слоёв также различаются. У [DataApi](../../integrations/nawserver/data_api.cpp)
команда `/api/data` ограничена 4096 байтами, включая CBOR-конверт команды;
16 KiB внутреннего значения не означает возможность записать такое значение
одним внешним POST. Предел HTTP-транспорта может быть меньше лимита адаптера,
поэтому принимается минимум действующих ограничений. Лимит 3584 байта в S3
относится к style-WS, а не к этим источникам или каталогу. Текущую эффективную
HTTP-границу нужно подтверждать конфигурацией/проверкой, не выводить из схемы.
В проверенной 2026-11-07 S3-конфигурации предел HTTP body также 4096 байт.

`DataValue` использует variant/map/vector/string. Построение значения уже
выделяет память до вызова `publish`; затем для проверки размера создаётся
временная CBOR-сериализация. В экспорте JSON появляются дополнительные деревья
и строки. Приём большого CBOR также требует памяти декодированного дерева.
Описания схем имеют ограничение глубины/ветвления, но отдельного общего бюджета
метаданных пока нет. Эти расходы нельзя выдавать за измеренный расход MCU.

Новые серии хранить в компактных типизированных кольцах с известной верхней
границей и без роста на каждом sample. Иллюстрация полезной нагрузки: 120 значений
float32 занимают 480 байт; две границы min/max — 960 байт. Служебное состояние,
валидность, выравнивание, публикуемый снимок и буферы кодека считаются отдельно.
Не нужно держать постоянно ещё одну универсальную копию всего кольца, если она
нужна только для экспорта; конкретный adapter и lifetime требуют проверки.

Устанавливать бюджет числа серий/точек и суммарных байтов до выделения новых
буферов, ограничивать очереди и обходы. Повторное включение не должно сохранять
брошенные кольца. При отключённом history-модуле не создаются его буферы,
таймеры, подписки и публикации. Отключение GUI-страницы само по себе не означает
отключение модуля. История в RAM не подразумевает запись Flash/NVS.

Для реальных гарантий нужны отдельные измерения persistent и peak RAM на S3:
регистрация, смена каталога, приём значений, экспорт capabilities/data, заполненная
история, открытие/уход со страницы и повторное отключение. На этом этапе это
план измерений, не опубликованные цифры.

## Что нужно агенту через MCP

Потребности будущего встроенного MCP определяются существующими сервисами:
фактические capabilities, выборочные данные и описания, чтение проекта,
раздельные preview/save и проверка revision. Это будущий native интерфейс;
удалённый посредник больше не предоставляет инструменты. Общие кодеки
остаются у редактора и сборочных инструментов. Офлайн-каталог не доказывает
наличие источников конкретной прошивки.

Расширить содержимое каталога и его обновление, сохраняя существующие API и
валидацию. Нужны описания полей/единиц/серий и доступность, актуальная ревизия,
а не новый инструмент на каждый датчик. Сырые значения читает `get_data`,
описания — `get_device`; выключенный/неизвестный источник не исчезает из знаний
агента только потому, что сейчас нет первого измерения.

Рабочий сценарий агента: прочитать actual capabilities и проект, выбрать данные
по описаниям, собрать новые страницы/стили/привязки, скомпилировать общим codec,
проверить preview и только затем отдельно сохранить. Политики preview/save/data
остаются независимыми; диагностика события не доказывает физическое касание.
См. [действующий MCP-контракт](../readme_mcp_ru.md).

### «Реестр реестров» и выдача по частям

Уточнение владельца: нужны доменные классификаторы, выбор части каталога и
компактная выдача для модели с небольшим контекстом. Это полезно как **иерархия
описаний внутри одного каталога**. Отдельные независимые хранилища данных со
своими правилами публикации для этого не нужны.

Предлагается группировка по модулям/доменам: `system`, `sensors`, `settings`,
`actions`, затем при необходимости небольшой следующий уровень. У группы есть
устойчивый ключ, короткое название, описание и число доступных записей. Источник
явно принадлежит группе; не нужно угадывать смысл по точкам в имени. Его полное
имя для биндинга остаётся прежним независимо от способа просмотра каталога.
При небольшом числе записей агент по запросу получает плоский список.
Группировка сама по себе не экономит RAM текущих копируемых descriptors.

Сначала ограничить нужно **весь discovery-ответ**, а затем каталог данных.
Нынешний `get_device` без аргументов возвращает INFO и полные capabilities:
виджеты/их методы, стили, ресурсы, данные и ограничения. Даже небольшой каталог
источников не делает этот совокупный ответ маленьким. Фильтрация только
`binding.sources` оставила бы остальной большой каталог в контексте модели.

Измерение обновлённой S3 от 2026-11-07: полный `/api/capabilities` — **43 618 байт
UTF-8**, сериализованное поддерево `binding` — **1180 байт UTF-8**, в нём три
источника и ноль действий. Это измерение конкретной прошивки, а не постоянные
размеры протокола. Число токенов из этих байтов не выводится. Оно показывает,
почему нужны выбираемые части общего capabilities, а не только группы данных.

Предлагаемое первое оглавление содержит разделы `device`, `widgets`, `styles`,
`data` и нужные сведения о ресурсах/проекте/лимитах. Краткий раздел устройства
сообщает совместимость и размер дисплея. Компоненты и методы раскрываются по
типу, стили — по семейству/нужным операциям, данные — по доменной группе и
источнику. Полные контракты по-прежнему доступны явно, когда они нужны задаче.
Это выбор частей существующих метаданных, не независимые копии их описаний.

Последовательность выдачи для раздела данных:

1. Короткая таблица групп с назначением и количеством источников/действий.
2. Перечень имён, названий и кратких типов выбранной группы.
3. Полная схема/поля только выбранных источников; значения и история запрашиваются
   отдельно. Большой массив показаний не прикладывается к каждому описанию.

Достаточно простых параметров раздела/группы/источника, уровня подробности,
`limit` и максимального размера UTF-8 ответа в байтах. Произвольный язык
запросов не нужен. Ограничение должно действовать и на список групп, и на список
записей; одна огромная схема/запись не должна тихо обрезаться в середине JSON.
Ответ явно сообщает завершённость, усечение и способ продолжить. Схему большого
источника можно раскрывать по пути поля, не выгружая всё дерево сразу.

Для меняющегося каталога continuation/offset привязать к `catalogRevision`.
Если ревизия изменилась между частями, вернуть явное требование перечитать список,
а не соединять куски разных каталогов. Сложный вечный серверный cursor/cache не
нужен: достаточно ревизии и позиции для текущего снимка. Конкретные имена
параметров и формат continuation здесь не утверждаются.

Универсального безопасного числа токенов «для слабой модели» нет: оно зависит
от модели, tokenizer, уже занятого контекста и задачи. Жёсткую гарантию backend
даёт в байтах и числе записей; host может дополнительно оценивать токены как
подсказку, выбирать меньшие порции и раскрывать только нужные детали. Предлагать
одну постоянную ёмкость для всех моделей было бы ложной гарантией.

Предпочтителен фильтр разделов/записей в существующем API с тем же сериализатором,
которым пользуются editor и MCP. Не заводить второй каталог исключительно для
агента и отдельный инструмент на каждую группу/датчик. Допустимый промежуточный
этап — фильтровать уже полученный каталог только в host MCP. Это сразу уменьшит
контекст модели, но **не уменьшит** построение полного ответа на MCU, его peak
RAM и сетевой трафик; такую границу нужно честно указать при приёмке.

## Варианты развития

| Вариант | Плюсы | Сложность и ограничения | Решение для начала |
| --- | --- | --- | --- |
| Расширить нынешний DataRegistry: метаданные, ревизия, управляемые динамические источники, opt-in история | Один каталог и путь данных; действующие биндинги/кодеки/MCP сохраняются; можно вводить по частям | Нынешние owned-схемы и универсальные значения продолжают расходовать RAM; нужны точные бюджеты | **Рекомендуется** |
| ROM/constexpr descriptions плюс owned-описания динамической части через общее представление | Снижает постоянный RAM фиксированных каталогов | Нужны модель lifetime, общий schema view и измерение экономии; static std::map задачу не решает | После измерения реального узкого места |
| Полностью описываемый CBOR граф обработки данных с произвольными связями | Максимальная настройка фильтров/производных источников без прошивки | Циклы, порядок вычисления, invalidation, ресурсы и диагностика становятся отдельным движком | Отложить; свободный дизайн страниц этого не требует |

## Паттерны и первичные источники

Реестр актуального состояния с типизированной публикацией и подписчиками —
установившийся подход. Например, [официальный Zephyr zbus](https://docs.zephyrproject.org/latest/services/zbus/index.html)
разделяет каналы и наблюдателей, описывает статические и runtime-каналы и
предупреждает о перезаписи сообщения до чтения подписчиком. Это подтверждает
необходимость отличать latest snapshot от потока всех отсчётов. Заимствуется
идея границ, не новая зависимость и не модель потоков Zephyr.

У LVGL 9.6 график уже имеет число точек, режимы shift/circular и отдельное
обозначение отсутствующей точки. См. [закреплённый публичный header](https://github.com/lvgl/lvgl/blob/v9.6.0/include/lvgl/widgets/lv_chart.h).
Запрошенный для сравнения [путь src/widgets/chart/lv_chart.h](https://github.com/lvgl/lvgl/blob/v9.6.0/src/widgets/chart/lv_chart.h)
в этой версии является переадресующим заголовком. Его API не делает историю
приложения постоянной: данные, живущие только внутри удалённого виджета,
удаляются вместе с ним. Вывод для нашей архитектуры — владение историей у
источника/обработчика, отображение у компонента. Это инженерный вывод из
границ владения, а не обещание готовой функции NaCBORUIforLVGL.

## Предлагаемый первый этап

1. Согласовать небольшую модель metadata, групп и стабильной идентичности без
   смены действующих типов/имён и без переписывания screen bindings; описать
   компактную и подробную выдачу частей одного каталога.
2. Добавить `catalogRevision` и доведение изменений каталога до существующих
   capabilities/MCP/editor, явно отделив это от revision значений и проекта.
3. Описать отключение и редкую перестройку динамических источников; проверить,
   что старый экран не получает показания другого датчика после перестановки.
4. Выделить один необязательный bounded history/filter модуль и проверить одну
   серию на системных или демоданных: неизменное число, разрыв, восстановление,
   сбор вне страницы, отключение. Функции вводить только по нужным сценариям.
5. Измерить память и только после этого выбирать ROM descriptors и дальнейшее
   уменьшение копий. Документировать действительные гарантии, не только CBOR bytes.

Имена новых полей/API, wire-совместимость, правила реального удаления и конкретный
адаптер графика ещё подлежат согласованию. В этом документе реализация этих
предложений не заявляется; принятые ранее ADR сохраняются без переписывания.

## Стенд проверки: сначала Windows

По уточнению владельца общий runtime и будущие изменения каталога/истории сначала
проверяются в настоящем LVGL под Windows. Фиксированные и динамические датчики
генерируются кодом через тот же вход DataRegistry/CBOR; UI получает обычные
проектные JSON/CBOR-описания. Проверки S3 дополняют этот цикл измерением памяти,
сетевой интеграцией и реальным дисплейным backend. Наличие Windows-рендера не
означает одинаковый расход памяти или покрытие всех плат аппаратной приёмкой.
