# Экраны, предпросмотр и исполнитель на МК

Проектная записка первого этапа, 2026-10-22. После неё реализован [MVP исполнителя экранов и компонентов](readme_screen_runtime.ru.md): там описаны действующий числовой wire-контракт, load/mount, границы и проверки. Ниже сохранены структура редактора и предложения развития; раздел «Предлагаемый исполнитель» не заменяет текущую спецификацию. Этот эскиз предшествовал реализации [биндингов и событий](readme_bindings.ru.md). На первом этапе `LV_USE_OBJ_PROPERTY_NAME` был отключён, а сборка на физическую плату не переносилась.

## Рабочее окно

В INFO справа находится самостоятельный `DeviceTasks.vue`. В «Компонент · стили» и редакторе отдельного экрана справа находится `PreviewPanel.vue`; вертикальный разделитель меняет ширину редактора и предпросмотра. `VirtualScreen.vue` независим от задач, WS и хранилища: получает ширину/высоту в пикселях, документ, шаг сетки, масштаб и выделенный ID; выдаёт выбор объекта. ResizeObserver пересчитывает автоматический масштаб по обеим осям контейнера. Ручной масштаб оставляет реальный размер документа и добавляет прокрутку. Сетка — редакторский слой поверх изображения, не padding и не элемент LVGL.

Одиночный компонент использует текущие собственные свойства именованного стиля. Тип и образец текста относятся только к предпросмотру: существующая демка МК по-прежнему работает со своим Label. Неизвестное содержимое `copy`/`merge` на устройстве не восстанавливается браузером. Корневой пункт «Экраны» открывает отдельную страницу управления документами (`ScreenManager.vue`), а дочерние пункты меню — редактор конкретного экрана. Ширина меню не меняется. На странице доступны добавление стандартного экрана или примера, переименование в строке, независимая копия, поиск по названию/ID, удаление и переход в редактор. Представления переключаются: компактная таблица, строки с предпросмотром каждого экрана и панели с одновременными миниатюрами. Выбранный вид сохраняется в `lvgl-cbor-screen-list-view`; по умолчанию используются строки с превью. Боковой панели предпросмотра на этой странице нет. `ScreenThumbnail.vue` использует общий `VirtualScreen.vue` с меньшими полями и без подписи масштаба; нажатие на миниатюру открывает редактор. CSS-предпросмотры приблизительные и не исполняют LVGL. Операции на странице списка не запускают автоприменение на МК. Редактор отдельного экрана содержит дерево, добавление/удаление/перестановку детей, выбор в дереве или на экране, параметры класса, стили и импорт/экспорт JSON. Удаление экрана имеет отмену; последний экран остаётся. Удаление узла сейчас сразу меняет локальный документ — перед большими экспериментами можно экспортировать JSON.

Размеры экранов и их содержимое сохраняются под `lvgl-cbor-screens-draft-1`. Настройки сетки, масштаба и размер экрана одиночного образца — под `lvgl-cbor-preview`. Стиль владельца в `lvgl-cbor-style-doc` остаётся отдельным. Сетка и масштаб не попадают в JSON для МК. При переключении режимов дерево не передаётся в старый канал стилей.

В панели предпросмотра отдельного экрана переключатель «Показать скрытые · 25%» включает отображение объектов с флагом `HIDDEN` (включая `common.add_flags`). По умолчанию они скрыты. Включённый режим ослабляет скрытую ветку до 25% исходной непрозрачности; вложенные HIDDEN не умножают это ослабление повторно. Скрытые объекты доступны для выбора; в Flex/Grid при показе они занимают место. Настройка сохраняется отдельно для ID каждого экрана в `lvgl-cbor-screen-preview-settings` и применяется также к его миниатюрам. Документ экрана, JSON/CBOR и флаг HIDDEN для устройства не изменяются.

## Почему не единая карта «всех CSS-параметров»

| Набор | Пример | Смысл в описании |
|---|---|---|
| Стиль | width, border, outline, shadow, Flex/Grid | Оформление и геометрия с выбором part/state |
| Параметры виджета | Label.text, Slider.value, Line.points | Данные конкретного класса; не наследуются как стили |
| Поведение | HIDDEN, SCROLLABLE, IGNORE_LAYOUT | Флаги объекта, управление вводом и размещением |
| Состояния | CHECKED, DISABLED, PRESSED | Выбор внешнего вида и логика ввода; часть состояний управляется устройством ввода |
| Дерево и команды | parent, порядок детей, удаление, загрузка экрана | Владение, порядок отрисовки и жизненный цикл |
| События и действия | CLICKED → application action | Символьное обращение к заранее предоставленной возможности приложения |
| Привязки | давление → Label.text | Подписки и преобразование данных; отдельный механизм |
| Ресурсы | шрифт, изображение, дорожки Grid, transition | Типизированные данные с явным временем жизни |
| Аппаратная среда | display, indev, driver, LVGL tick | Предоставляется прошивкой; не создаётся произвольным экраном |

В LVGL действительно есть [Widget Property API](https://lvgl.io/docs/open/common-widget-features/obj_property): `lv_obj_set_property`, `lv_obj_get_property`, пакетная установка и поиск имени при `LV_USE_OBJ_PROPERTY_NAME`. Оно включается через `LV_USE_OBJ_PROPERTY`, покрывает не весь C API и имеет свойства только для чтения. Наличие этого API уменьшает число собственных адаптеров, но не решает владение строками/массивами, составные вызовы, создание объектов и подписки. Внутренние Property ID LVGL не делаем нашим межверсионным ABI. Подробный [HTML-каталог](widget_api_lvgl_9_6.html) построен по закреплённым исходникам 9.6.0; он показывает реальные setter/getter и C-сигнатуры.

## Минимальная форма JSON

Точный пример: [example.screen.json](../contracts/screens/example.screen.json). Формальная структура: [screen-draft-1.schema.json](../contracts/screens/screen-draft-1.schema.json). Генератор: `node tools/build_screen_schema.mjs`.

```json
{
  "format": "lvgl-screen-draft-1",
  "id": "dashboard",
  "name": "Приборы",
  "size": { "width": 800, "height": 480 },
  "styles": {
    "caption": { "props": { "text_color": "#ffffff" } }
  },
  "root": {
    "id": "root",
    "type": "obj",
    "style": {
      "layout": "LV_LAYOUT_FLEX",
      "flex_flow": "LV_FLEX_FLOW_COLUMN",
      "pad_all": 16,
      "pad_row": 8
    },
    "children": [
      {
        "id": "pressure",
        "type": "label",
        "props": { "text": "--" },
        "styles": [{ "ref": "screen:caption", "part": "MAIN", "state": [] }],
        "style": { "width": { "pct": 100 }, "height": "content" }
      }
    ]
  }
}
```

Один файл описывает один экран. Каталог редактора — список таких документов; будущий стартовый экран выбирает приложение/проект, а не вложенный документ. Имя для человека можно менять независимо от `id`. ID узлов уникальны внутри экрана и остаются символьными UTF-8. Дерево вложенное, поэтому второго поля parent с риском противоречия нет. Порядок массива children задаёт порядок создания и базовый z-order. Корень — `obj` без родителя; его размер задаёт `size`, а не node.style.width/height. В будущем согласовать изменение разрешения с реальным дисплеем: создание экрана само по себе не перенастраивает LCD.

`style` — сокращённая запись собственных свойств MAIN/DEFAULT. `styles` — упорядоченное подключение общих стилей по ссылке; это не merge. `styleRules` — собственные стили других part/state, например `{ "part":"INDICATOR", "state":[], "props":{...} }`. Первое браузерное приближение показывает MAIN/DEFAULT, остальные части виджетов пока нейтральные; содержимое импортированных правил сохраняется. Неизвестные/глобальные ссылки браузер не разрешает и должен показывать это как ограничение, а не подменять готовым стилем.

В черновике определения `styles` содержат только `props`. Для следующего расширения использовать уже принятую семантику copy → ordered merge → own props существующего именованного стиля, без новых областей владения. Внешние ссылки `global:name` предоставит приложение. Добавление полей copy/merge потребует расширения схемы и валидатора; оно не реализовано этим редактором.

`props` типизирован по классу. Первый набор: obj, label, button, bar, slider, arc, line, image, checkbox, switch, textarea, dropdown. Общее поле `text` не означает, что у каждого C-класса есть setter текста: для Button это удобство автора, которое будущий компилятор раскроет в дочерний Label. Такой служебный ребёнок получает внутренний handle, не публичный ID и не может затенить авторский узел. Для полной управляемости можно явно создать Label внутри Button. `min/max` передаются адаптеру диапазона до `value`; анимация во время загрузки выключена. `checked` у Switch/Checkbox компилируется в состояние CHECKED, а не вторую независимую копию состояния.

`flags` — карта явных включений/выключений относительно стандартов класса. Отсутствие флага отличается от false. Не переносить в документ адреса `lv_obj_t*`, callback, `user_data` или содержимое драйвера.

## Размерности и Grid

Число — пиксели. `{ "pct": 100 }` — процент от области родителя по правилам LVGL. `"content"` — LV_SIZE_CONTENT. Не сохранять битовое представление `LV_PCT()`/служебные числовые sentinel в JSON. Поддержанные формы в браузерных полях размера: `120`, `100%`, `content`. На МК эти формы компилируются в значения LVGL с отдельной проверкой допустимости по свойству.

Для Grid имена свойств остаются LVGL, но указатели заменены данными:

```json
{
  "layout": "LV_LAYOUT_GRID",
  "grid_column_dsc_array": [120, { "fr": 1 }, { "fr": 2 }],
  "grid_row_dsc_array": ["content", { "fr": 1 }],
  "grid_cell_column_pos": 0,
  "grid_cell_column_span": 2,
  "grid_cell_x_align": "LV_GRID_ALIGN_STRETCH"
}
```

Параметры `grid_cell_*` задаются ребёнку, массивы дорожек — родителю. МК выделяет стабильные int32-массивы и добавляет LV_GRID_TEMPLATE_LAST. Они живут до удаления всех использующих их объектов/стилей. FR и content переводятся через LV_GRID_FR/LV_GRID_CONTENT. Браузер переводит их в CSS Grid. Колонки/строки нумеруются с нуля в JSON, с единицы в CSS. Перенос Flex, grow и выравнивание переводятся в CSS Flexbox, но CSS shrink выключен: это важное отличие браузерных значений по умолчанию.

Layout в документе экрана имеет символическое имя `LV_LAYOUT_NONE/FLEX/GRID`. Будущий `custom:radial` должен разрешаться приложением в ID, полученный в этом запуске `lv_layout_create()`. Сам callback документ не приносит. Числовые runtime ID нестабильны и не должны закрепляться в файлах экранов. Старый редактор shared-style пока сохраняет прежний числовой layout ради совместимости со своей прошивкой.

## Предлагаемый исполнитель на МК

Это план реализации, не описание уже существующих C++ функций.

1. **Capabilities.** Приложение публикует версию схемы, shared ABI/hash, доступные классы, свойства/операции, ресурсы, layout-имена и ограничения. Наличие метода в общем HTML не означает, что он скомпилирован на плате. Согласовать лимиты объектов/глубины/строк/массивов/стилей и bytes до загрузки. Текущие ограничения пакета и 8 стилей на scope относятся к старому стенду; применять их к целому экрану автоматически нельзя.
2. **Декодирование и проверка без изменения активного экрана.** JSON на ПК → CBOR. Имена экранов/узлов/полей приложения остаются UTF-8. Стили можно компилировать в уже закреплённые shared opcodes; остальные семейства получают собственные версионированные правила только после утверждения. Нельзя использовать неограниченный «вызов C-функции по имени».
3. **Промежуточный план.** Проверить ID, классы, связи, типы, диапазоны, part/state, ресурсы, ссылки на стили, диапазоны Slider/Arc, длины массивов. Ошибка содержит путь JSON, node ID и причину. Создание в UI-task, блокировка/контекст LVGL согласованы с приложением.
4. **Staging.** Создать новый корневой экран вне активного дерева. Построить экранные стили и ресурсы; создать объекты родитель → дети через фиксированную таблицу фабрик; записать ID → lv_obj_t*. Применить параметры в определённом порядке, затем стили/селекторы и флаги. Вызвать обновление layout после создания дерева. При любом сбое удалить staging и освободить его ресурсы; старый экран остаётся.
5. **Commit.** После успешной подготовки загрузить экран; подтвердить document revision/hash. Анимации перехода и удаление старого экрана требуют отдельного завершения: нельзя освобождать его стиль в начале анимации. Если памяти на два дерева мало — вернуть ошибку бюджета либо использовать явно выбранную разрушительную загрузку; не обещать атомарность без двойного дерева.
6. **Обновления редактора.** Сначала полная замена документа. Затем добавить ограниченный patch по node ID и revision: последнее значение в очереди, один запрос в полёте, подтверждение применённой revision и реальные bounds. Патчи структуры, ресурсов и параметров не обязаны разделять транзакционность. UI не должен принимать старый ACK за подтверждение нового состояния.
7. **Unload.** Сначала отключить callbacks/подписки и отменить отложенные действия, удалить объекты, затем освободить экранные lv_style_t, строки/массивы/ресурсы. Стабильный адрес именованного стиля сохраняется при его замене. Глобальные стили и ресурсы принадлежат приложению и не освобождаются экраном.

Владение: CBOR может быть освобождён после создания только если всё сохраняемое скопировано или имеет независимый owner. `lv_label_set_text` копирует текст, варианты `_static`, таблицы options/points/tracks и указатели на ресурсы могут требовать долгой жизни. Не обобщать один договор памяти на все setter. Для каждого адаптера пометить copy/borrow и порядок удаления. Выделение памяти/пиковый heap нужно измерить на реальном экране; численной экономии пока не обещаем.

Практический C++ слой: ScreenRuntime хранит root, ID-map, arena строк/массивов, стабильные screen-style slots и список подписок. WidgetAdapter знает factory, типизированные property-setters, их порядок и владение. Для части данных можно использовать generic Property API, для составных методов — явные адаптеры. Нативный код может получить объект по ID и управлять им; следующая декларативная замена определённых полей перекроет такие изменения.

## События, биндинги и переиспользуемые компоненты

В первом эскизе привязки и события отсутствовали в JSON-схеме. Первый MVP допускал только пустое `bindings:[]`. Актуальный формат описан в [руководстве биндингов и событий](readme_bindings.ru.md). Язык привязок не закрепляется преждевременно. Следующий слой не должен мешать загрузке обычного статического дерева. Событие в будущем связывает символ LV_EVENT_* с символом разрешённого действия приложения и типизированными аргументами; произвольный C/JS не исполняется. Повторное нажатие и отказ приложения нуждаются в явной политике.

Биндинги развивают [согласованную рабочую модель](readme_bindings.ru.md): именной реестр, зависимости и спрос; постоянные подписки переживают переключение экранов, экранные снимаются при уничтожении. Неизвестное значение отображается `--`, а не нулём. UI-task отсекает обновления прошлой generation экрана. Самый первый пример: давление из реестра → Label.text с форматом и отсутствующим значением. Не заменять базовые биндинги одним недостаточным where-равенством и не вводить полный язык скриптов без отдельного решения.

Переиспользуемые шаблоны компонентов логично раскрывать на ПК в обычное дерево до передачи МК. Тогда runtime остаётся простым, а сервер/браузер берёт на себя namespaces, параметры и повторение. Если понадобится создание из шаблонов на МК — это отдельная capability и версия схемы, а не скрытое требование первого загрузчика.

## Границы браузерного приближения и следующие проверки

CSS сейчас показывает пиксельные/процентные размеры и ограничения, padding/margin, позиции и основные align, Flex/Grid, фон и простой градиент, border/outline с разными шириной/цветом/opa, shadow и drop_shadow, текст, основные трансформации и образцы 12 классов. Не реализованы точные темы/шрифты LVGL, все части и состояния, сложные градиенты и masks, реальный ввод/инерция, анимации, callbacks/биндинги, пользовательские layout. Изображение по символическому имени показывается заглушкой до появления отображения ресурсов; data:image и blob могут показываться локально. В панели перечисляются явно заданные неподдержанные style keys.

Необходимо сравнить CSS и native LVGL на одинаковых эталонах: padding+border+min/max; wrap+grow; Grid px/content/FR+spans; длинный многострочный текст; overflow; transform; part/state. Затем измерить MCU staging/commit/unload, отказ при нехватке памяти, повторные замены и запоздалые события. Сборка браузера и unit-тесты не подтверждают физическую отрисовку LCD.
