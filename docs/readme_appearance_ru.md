# Пользовательские схемы и стек стилей

Схема может менять цвета, радиусы, рамки, линии, отступы и состояния. Она не
ограничена палитрой. Flex/Grid и структура страницы остаются обычным описанием
экрана, которое также редактируется через MCP. Исполнение стилей использует
существующий StyleService/StyleRuntime и LVGL; отдельного theme engine нет.

## Демонстрация Windows

```powershell
npm run player -- examples/windows_player/registry-demo.json `
  --schemes examples/windows_player/registry-schemes.json --no-settings
```

На одной странице находятся кнопки:

| Вариант | Вид |
| --- | --- |
| Строгая классика | Светлый фон, синие акценты, прямые углы |
| Космическое будущее | Тёмный фон, голубые линии, угловатые элементы |
| Розовый пони | Светло-розовый фон, розовые акценты, округлые элементы |

Нажатие вызывает обычное действие `ui.select_scheme`; источник `ui.scheme`
подтверждает выбор, биндинги обновляют подпись и checked-состояние кнопок.
Объекты и подписки не пересоздаются при смене этой прикладной схемы.
Старый каталог с четырьмя схемами остаётся стандартным для основной демки.

`--schemes` принимает собственный файл `nacborui-windows-schemes-1`. В нём от 1
до 8 вариантов с произвольными ID: `[a-z][a-z0-9_]{0,11}`. Указанный default обязан
существовать. У каждого варианта name и десять обязательных цветов:
canvas, surface, surfaceAlt, border, text, muted, bar, barText, primary, hover.
Дополнительный `roleOverrides` задаёт обычные props существующей стилевой роли:

```json
{
  "button": {"radius": 14, "border_width": 1, "border_color": "#943d68"},
  "panel": {"radius": 18, "border_width": 1},
  "button_focus": {"outline_width": 2, "outline_pad": 2}
}
```

Это содержимое roleOverrides внутри варианта, не целый файл. Полный пример —
[registry-schemes.json](../examples/windows_player/registry-schemes.json).
Неизвестная роль отклоняется; свойства, типы и доступные ресурсы проверяются
общим стилевым кодеком. Его ограничения не обходятся этим форматом.

Палитра/геометрия роли меняются заменой содержимого её стабильного стиля и
`lv_obj_report_style_change`. Локально заданный у компонента цвет или radius
может перекрыть схему — такой override следует оставить только сознательно.
Число ролей и действия Appearance принадлежат примеру, не публичному UI-ядру.

## Несколько стилей на одном компоненте

Узел в проекте может выглядеть так (фрагмент):

```json
{
  "id": "apply", "type": "button", "props": {"text": "Apply"},
  "styles": [
    {"ref": "global-dynamic:design.button"},
    {"ref": "screen:button_size"},
    {"ref": "global-dynamic:design.focus", "state": ["FOCUSED"]},
    {"ref": "screen:focus_override", "state": ["FOCUSED"]}
  ]
}
```

В примере Windows кнопки выбора соединяют глобальную роль Appearance, экранную
геометрию и несколько состояний. Экранный focus_override, прикреплённый позже
при том же selector, перекрывает outline_width, а цвет контура остаётся у общей
роли. INDICATOR/KNOB переключателей и ползунка имеют свои ссылки стилей.

Учитывайте реальную специфичность part/state в LVGL. Нельзя свести любой спор
свойств к фразе «последний всегда победит»: влияет selector, локальный стиль и
наследование поддерживаемых свойств. Вложенная страница имеет собственный screen
scope и может переиспользовать общие глобальные стили проекта.

`copy/merge` при построении именованного стиля дают снимок свойств. Прикрепление
нескольких самостоятельных стилей даёт стек. Изменение исходного copy/merge само
не пересобирает производный стиль; изменяемые прикреплённые стили обновляют объекты.

## Новое оформление через MCP

Новые стили — обычные документы проекта. Для этого не требуется добавлять новый
ID в C++, собирать прошивку или придумывать отдельный инструмент set_theme.

1. `get_device({})`: размеры, разделы discovery. Затем `get_device` с
   `section:"styles"`, а для нужного метода — name, например `radius`.
   `section:"resources"` показывает реальные шрифты/изображения/стили приложения.
   `get_data_catalog` раскрывает доступные данные и действия.
2. `read_project({})` получает актуальный проект и его revision. Сохраняйте биндинги,
   события, страницы и ресурсы, которые нужны новой компоновке.
3. Создайте именованные документы в `project.styles`, например:

   ```json
   {
     "design.button": {
       "scope": "global", "name": "design.button", "attach": false,
       "props": {"bg_color": "#a63f73", "bg_opa": 255, "text_color": "#ffffff", "radius": 14}
     },
     "design.focus": {
       "scope": "global", "name": "design.focus", "attach": false,
       "props": {"outline_color": "#a63f73", "outline_width": 2, "outline_pad": 2}
     }
   }
   ```

   Это фрагмент project.styles; имена ключа/документа должны совпадать. Прикрепите
   их к узлам через `global-dynamic:` и `styles[]`. Нужные геометрию и состояния
   можно оставить отдельными стилями. Уберите мешающие локальные overrides.
4. `compile_document({kind:"project",document:project})` проверяет проект общим
   кодеком с настоящими capabilities; `preview_project({project,screen})` показывает
   несохранённый вариант. screen берётся из проекта, а не предполагается по названию.
5. После проверки `save_project({project,revision})` сохраняет явно. Альтернатива
   для одной правки — `write_project_document({kind:"styles",name,document,revision})`.
   Сохранение одного style не добавит недостающие ссылки на него в экран: для
   согласованного редизайна удобнее целый проект одной транзакцией.

Preview и save имеют независимые разрешения MCP и разные эффекты. Preview не
пишет storage, save не переключает дисплей. При конфликте revision перечитайте
проект. Ошибка компиляции не заменяет текущий рабочий UI.

Произвольное оформление, созданное MCP таким способом, становится содержимым
проекта. Оно не добавляется автоматически в отдельное прикладное меню Appearance:
это каталог ресурсов Windows-примера. Для нескольких выбираемых вариантов внутри
переносимого проекта используйте обычные страницы/ссылки и события либо прикладной
каталог схем; общего скрытого реестра «магических тем» в ядре нет.

Проверка `test-catalog.mjs` использует настоящий stdio MCP и нативный LVGL через
штатный NaWServer. Это доказывает общий путь JSON → CBOR → runtime.
Для работы на запущенном Windows-проигрывателе теперь доступен
[постоянный HTTP API и проектный MCP](readme_windows_api_ru.md), проверяемые
сквозным production test-api.mjs. Устройство использует тот же MCP
через свой штатный проектный API. См. [MCP](readme_mcp_ru.md),
[каталог данных](readme_data_catalog_ru.md) и
[приёмку](reviews/REVIEW_20261107_data-catalog-history.md).
