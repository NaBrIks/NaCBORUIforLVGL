# Графика LVGL: что доступно через CBOR и что разумно для МК

Проверено 2026-11-07 по закреплённой LVGL **9.6.0**, текущему screen ABI v3,
C++-исполнителю и профилям S3/Windows. Это анализ существующих возможностей и
направлений развития. По следующему поручению владельца добавлена отдельная
Windows-галерея настоящих LVGL decoder/vector/Canvas путей. Общий MCU ABI не
расширен; сравнительные FPS/время кадра на МК не измерялись.

Для приборной панели на слабом МК разумная основа — **обычные виджеты, линии и
дуги для меняющихся показаний, готовые растровые ресурсы для сложного декора**.
SVG/полные векторные пути стоит подключать по конкретной необходимости.
Гладкий график не требует переводить весь интерфейс на SVG.

## Вектор, растр и кривая — разные уровни

Вектор хранит геометрию: точки, команды пути, контуры, заливки. Растр хранит
готовые пиксели. На обычный LCD в итоге в обоих случаях передаются пиксели:
геометрию сначала нужно растеризовать. Сам формат CBOR на стоимость этой
растеризации не влияет: он компактно передаёт описание, а рисует LVGL.

`lv_draw_line`, `lv_draw_arc`, границы и закругления уже дают геометрическую
графику без полного SVG/ThorVG. Это отличается от необязательного LVGL
Vector API для составных путей с Bézier, сложными заливками и преобразованиями.
В проверенной S3 используется программное рисование; аппаратный векторный draw
unit не подключён. Возможности software renderer описаны в
[официальной документации Draw Units](https://lvgl.io/docs/open/main-modules/draw/draw_units).

У гладкой кривой есть два практических представления:

- **Ломаная с достаточно частыми точками.** Форму Bézier можно один раз рассчитать
  на ПК, сохранить как XY и показать уже существующим `line.points`. На МК нет
  вычисления самой кривой; остаётся отрисовка её отрезков. При изменении размера
  или формы точки нужно обновить. Это приближение, не точный векторный контур.
- **Квадратичный/кубический путь Bézier.** Хранятся опорные и управляющие точки;
  renderer сам получает пиксели кривой. В LVGL есть `lv_vector_path_quad_to` и
  `lv_vector_path_cubic_to`; наш CBOR ABI их пока не экспортирует. См.
  [Vector API закреплённой версии](https://github.com/lvgl/lvgl/blob/v9.6.0/include/lvgl/draw/lv_draw_vector.h).

Не путать сглаживание изображения с усреднением измерений. Интерполяция меняет
вид между отсчётами, фильтр меняет сами значения. Произвольный сплайн способен
нарисовать пик между измерениями, которого в данных не было. Для технических
измерений исходный вариант — ломаная; при необходимости сглаживания выбирать
алгоритм без нежелательных выбросов и сохранять исходные значения. Пропуски
измерений должны оставаться разрывами, а не соединяться красивой кривой.

## Что уже есть и чего нет в нашем ABI

«Native» ниже означает обычную регистрацию C++-компонента через WidgetRegistry
с фабрикой, исполнителем и машинным каталогом методов. Это существующая точка
расширения, а не обещание уже написанного адаптера. Фактическая доступность
определяется capabilities конкретной сборки.

| Механизм | LVGL 9.6.0 | Наш CBOR сейчас | Native-путь / ограничение | Профили S3 и Windows |
|---|---|---|---|---|
| Прямоугольники, фон, рамки, радиусы, цвета | Есть | `obj` и экспортированные свойства style ABI v2 | Дополнительный код не нужен для свойств из контракта | Обычный software renderer |
| Линия/ломаная | `lv_line` | `line`, `points`: 2–256 целочисленных XY | Буфер точек хранится runtime; координаты −32768…32767 | Доступна |
| Дуга и круговая шкала | `lv_arc`, draw arc/rect | `arc`: range/value/angles/bg_angles/rotation/mode; круг возможен через стиль объекта | Низкоуровневые `lv_draw_arc` — внутри native draw callback | Доступна |
| Картинка, поворот, масштаб | `lv_image` | `image.src/scale/rotation` | `src` — имя уже зарегистрированного ресурса `const void *` | Виджет доступен; декодеры зависят от сборки |
| Произвольные draw-команды: линия, треугольник, текст, дуга | Draw API | Общего CBOR-потока draw-команд нет | Уже используются native-компонентами S3 | Примитивы доступны |
| Canvas: рисование в собственный пиксельный буфер | `lv_canvas` | Нет встроенного типа/методов canvas | Нужен native-адаптер с явным владением и лимитом буфера | В LVGL включён, через наш ABI не открыт |
| Графики LINE/BAR/SCATTER, несколько серий | `lv_chart` | Общего chart-адаптера нет | Можно зарегистрировать компонент с ограниченными сериями | В LVGL включён, через наш ABI не открыт |
| Гладкий `LV_CHART_TYPE_CURVE` | Есть | Chart-адаптера нет | Использует Vector API; при выключенном vector в исходниках 9.6 возвращается к LINE | В S3 выключено; в Windows-галерее включено |
| Составной путь, quadratic/cubic Bézier, stroke/fill | Vector API | Нет команд пути | Нужен ограниченный native-адаптер и подходящий draw unit | S3: выключены; Windows-галерея: включены |
| SVG Tiny 1.2 | Парсер/renderer и SVG image decoder | Inline SVG и загрузки SVG-ресурса в project ABI нет | После отдельного включения может быть image-ресурсом либо native-отрисовкой | S3: выключен; Windows-галерея: включён |
| Lottie | `lv_lottie` + ThorVG; отдельная legacy-интеграция Rlottie | Нет | Нужны адаптер, renderer и буфер кадра | Lottie/Rlottie выключены |
| Наш график истории | Примитивы LVGL | `demo:history_plot`, метод `series` | Только Windows-пример: подпись + 32 отсчёта, ломаная; не `lv_chart` | Зарегистрирован в Windows, не обещан S3 |
| Наш спидометр/радар | Draw API | Каталоги `lab:speedometer`, `lab:radar` | Native-примеры S3; геометрия задаётся их C++-кодом и опубликованными параметрами | Это отдельные demo-компоненты |

Наличие функции в справочнике всего LVGL не означает наличия её команды в
NaCBORUIforLVGL. А наличие виджета, скомпилированного в LVGL, не означает, что он
зарегистрирован в нашем runtime.

При анализе найден и исправлен разрыв проверок: раньше PC-кодек ограничивал
число точек `line.points` до 2–256, а C++ проверял бюджет памяти и координаты.
Теперь generated line-handler проверяет те же границы до выделения/копирования
массива точек. Общий `PointSpan` сторонних native-компонентов не сужен.
[Raw-CBOR native-регрессия](../tests/native/screens.cpp) непосредственно создаёт
wire-пакеты: 2/256 точек принимаются, 1/257 отвергаются, прежние экран и линия
сохраняются. Существующий `screen_runtime_tests` прошёл; wire ABI и hash не
менялись. Новые path/chart должны аналогично проверять свои границы на МК.

Это не свидетельство включённого `lv_draw_vector`/ThorVG: он рисует обычные линии,
дуги, треугольник стрелки и подписи через draw callback.

## Bézier-график и произвольный векторный рисунок

Для графика значения, временная шкала, окно истории, пропуски и диапазон осей
важнее формата графического пути. История принадлежит источнику/модулю данных;
виджет её отображает. Переключение страницы не должно обнулять измерения.
Существующий Windows history plot уже следует этому разделению.

В LVGL `lv_chart` есть собственные серии и режимы SHIFT/CIRCULAR, внешние массивы
значений и специальная оптимизация LINE при числе точек больше числа пикселей
по горизонтали. Для LINE она сохраняет минимумы/максимумы внутри пиксельного
столбца. CURVE требует векторного renderer. См.
[официальный Chart](https://lvgl.io/docs/open/widgets/chart).
В закреплённом исходнике [ветка CURVE](https://github.com/lvgl/lvgl/blob/v9.6.0/src/widgets/chart/lv_chart.c)
проверяет `LV_USE_VECTOR_GRAPHIC` и при его отсутствии рисует LINE. Поэтому
одного выбора CURVE в будущем CBOR-адаптере недостаточно.

Для изменяемого живого графика лучший первый шаг — небольшой общий адаптер
`lv_chart` либо развитие ограниченного plot, а не экспорт всего SVG. Для
статичной декоративной кривой достаточно заранее подготовленной ломаной или
картинки. Возможный путь Bézier нужен для рисунков, которые действительно
постоянно меняют форму/масштаб; это самостоятельная необязательная возможность.

## Цена памяти и процессора

Ниже арифметика объёма данных, не измерения всей программы. Stride, выравнивание,
поля объектов, allocator, decoder, draw layer и cache требуют дополнительной
памяти. Один такой буфер не заменяет обязательные буферы дисплея.

| Данные | Полезный объём без накладных расходов |
|---|---:|
| 128 значений float32 | 512 Б |
| 128 значений float32 + 128 timestamp64 + битовая маска достоверности | 1552 Б |
| N точек `line` | `N × sizeof(lv_point_precise_t)`; при двух 32-битных координатах 256 точек — 2048 Б |
| Иконка 32×32 RGB565 | 2048 Б |
| Маска иконки 32×32 A8, цвет задаётся отдельно | 1024 Б |
| Canvas/кадр 100×100 ARGB8888 | 40 000 Б, около 39,1 КиБ |
| Canvas/кадр 200×100 ARGB8888 | 80 000 Б, около 78,1 КиБ |
| Полный 800×480 RGB565 | 768 000 Б, 750 КиБ |
| Полный 800×480 ARGB8888 | 1 536 000 Б, 1500 КиБ |

Canvas хранит пиксели в живущем вместе с ним буфере. При удалении владельца
динамический буфер освобождается; временный массив на стеке обработчика для
него непригоден. Это прямо описано в
[Canvas](https://lvgl.io/docs/open/widgets/canvas). Lottie дополнительно хранит
анимацию и растеризует текущий кадр в выделенный буфер; подробнее
[Lottie](https://lvgl.io/docs/open/widgets/lottie).

Сам векторный путь может занимать меньше места, чем большая картинка, но парсер,
список операций, управляющие точки и рабочая память renderer тоже имеют цену.
В LVGL 9.6 контейнеры vector path способны перераспределять память при росте.
Для будущего MCU-адаптера необходимы верхние границы до построения пути, а не
надежда на то, что исходный SVG/CBOR маленький.

У SVG нет универсального требования всегда держать полный ARGB-растр: в
[decoder 9.6](https://github.com/lvgl/lvgl/blob/v9.6.0/src/image/svg/lv_svg_decoder.c)
строится подготовленный draw list, который может кэшироваться. Стоимость
парсинга и повторной растеризации — разные вещи. Сохранённый путь/draw list
убирает повторный разбор, но не делает бесплатным рисование изменяемого кадра.

Для CPU важны одновременно количество сегментов, площадь изменившихся пикселей,
толщина/сглаживание, прозрачность, слои, тени и частота обновления. Простой путь
иногда дешевле большой прозрачной картинки; сложный SVG на каждом кадре может
быть дороже готового изображения. Формат сам по себе не определяет победителя.
PSRAM добавляет вместимость, но не отменяет стоимость доступа и смешивания
пикселей. Windows-тест не является замером быстродействия ESP32.

## Практический выбор

| Задача | Предпочтительный первый вариант |
|---|---|
| Меняющиеся цифры, цвет состояния, заполнение, положение стрелки | Обычные LVGL-виджеты/примитивы и биндинги; обновление только нужного объекта |
| 1–несколько живых графиков | Ограниченные серии, ломаная, число точек по видимому разрешению; аккуратное прореживание с сохранением пиков |
| Сложный логотип/декор фиксированного размера | Подготовленный растр; компактная маска + цвет для одноцветной иконки |
| Один декор в нескольких известных размерах | Несколько заранее подготовленных размеров либо один подходящий по качеству растр; оценить Flash против RAM/CPU |
| Редко меняющаяся кривая | Рассчитать/тесселировать при смене данных или размера и переиспользовать точки |
| Необходимый произвольный масштаб/форма, сложные контуры | Необязательный Vector/SVG-профиль с бюджетом операций и отдельной проверкой на целевом МК |
| Декоративная анимация | Сначала простое изменение угла/позиции/значения; Lottie подключать, когда эффект оправдывает буфер и renderer |

Кэшировать следует то, что действительно используется повторно: рассчитанные
точки, разобранный путь либо небольшой готовый растр. Удерживание всех вариантов
и всех размеров сразу экономит CPU ценой RAM. Достаточны явные лимиты и
освобождение по жизненному циклу экземпляра; отдельная универсальная система
кэширования ради одного графика не требуется.

На практике подходит гибрид: **растровая шкала/декор + геометрическая стрелка,
обычный текст и график по данным**. Изменение угла стрелки не требует повторно
декодировать фон. Но итоговую площадь перерисовки всё равно определяет LVGL и
компоновка: минимальная CBOR-команда сама по себе не гарантирует минимальную
площадь redraw.

## Что мешает полностью менять оформление только документом

CBOR уже меняет дерево зарегистрированных компонентов, вложенность, Flex/Grid,
цвета и поддержанные стили, подписи, состояния и опубликованные параметры native
компонентов. Он не добавляет исполняемый C++ или отсутствующий декодер.

Сейчас `image.src` разрешает имя существующего ресурса, а не произвольный путь,
URL или новые пиксели внутри документа. Поэтому полноценный перенос нового
набора иконок потребует отдельно продуманного ресурса с форматом, размером,
владельцем и ограничением декодирования. Это ограничение слоя ресурсов, не
недостаток CBOR. Возможности самого LVGL Image шире нашего экспортированного
метода: [Image](https://lvgl.io/docs/open/widgets/image).

Если добавлять новые входы, минимальные направления такие:

1. **График:** количество серий/точек, оси, единицы, данные и пропуски; схема
   значений публикуется общим каталогом. История/усреднение остаются у источника,
   а не возникают заново для каждого видимого графика.
2. **Ресурс изображения:** формат, размеры, доступное хранение и явные лимиты
   байтов/декодированной площади. Одна регистрация/загрузка, затем ссылки по имени.
3. **Только при реальной потребности — path:** небольшой конечный набор
   move/line/quad/cubic/close, stroke/fill, ограниченные сегменты и координаты.
   Это данные для renderer, без скриптов и произвольных callback из документа.

Все три следует подключать через существующие контракты/capabilities и native
регистрацию. Не нужны отдельный движок, особый MCP для спидометра и копия реестра
данных только для графики. Цветовые схемы должны влиять на семантические стили,
а не требовать повторной генерации всех геометрических ресурсов.

## Флаги и источники

Для закреплённой версии правильное имя — **`LV_USE_VECTOR_GRAPHIC`**, в
единственном числе. Программному vector renderer нужны `LV_USE_MATRIX`,
`LV_USE_VECTOR_GRAPHIC` и `LV_USE_THORVG`; `LV_USE_THORVG_INTERNAL` выбирает
встроенную реализацию ThorVG. Для SVG нужен ещё `LV_USE_SVG`, для Lottie —
`LV_USE_LOTTIE`. Другой подходящий аппаратный draw unit заменяет программный
ThorVG-путь, но не появляется от одного изменения флага.

Веб-руководства иногда сохраняют старые имена `_EXTERNAL` или неполный список
зависимостей. Приоритет для этой сборки —
[lv_conf_template.h тега v9.6.0](https://github.com/lvgl/lvgl/blob/v9.6.0/lv_conf_template.h),
[проверки Vector API](https://github.com/lvgl/lvgl/blob/v9.6.0/src/draw/lv_draw_vector.c)
и реальный конфиг target. В MCU-профиле S3 vector/ThorVG/SVG/Lottie выключены. Windows-галерея отдельно
включает vector/ThorVG/SVG; Lottie остаётся выключенным. Одно изменение
документа/CBOR не включает отсутствующий в сборке decoder.

SVG-парсер LVGL ориентирован на SVG Tiny 1.2, а не на полную HTML/CSS/SVG-среду
браузера. Официальные примеры загрузки и draw-event пути приведены в
[SVG Decoder](https://lvgl.io/docs/open/libs/image_support/svg).

Дополнительно: [нативные компоненты](readme_native_components_ru.md),
[биндинги](readme_bindings_ru.md),
[Windows-проигрыватель](readme_windows_player_ru.md).

| Настройки | Четыре схемы и обычные demo-контролы генератора/уровня/счётчика |

Исходный системный `demo.json` не подменяется. Базовая компоновка — 1280×800:
образцы каждой группы видны совместно. При уменьшении окна Flex переносит
образцы; вертикальной прокруткой владеет соответствующая страница, а не shell.
У всех 19 образцов **одна и та же шахматная подложка** — общий RGB565 resource
и обычный `image` перед изображением/кривой в дереве. Прозрачные поля native
sample/Canvas не закрашивают её. Образцы подписаны по-русски: «непрозрачное»,
«альфа 0..255». A8 хранит только маску прозрачности, цвет задаётся стилем.
JPEG, выбранные BMP/RGB565/I4 и наш GIF непрозрачны; произвольной alpha у GIF
нет. PNG/ARGB/A8 и Canvas показывают прозрачность. GIF имеет восемь кадров
по 120 мс; его независимый LVGL timer не останавливается вместе с генератором.

Собственный MIT `landscape.svg` содержит 21 цветной SVG path: слои холмов,
квадратичные/кубические кривые, солнце, деревья, птицы и дом. Это исходный SVG,
который разбирает и рисует LVGL, без предварительного превращения в PNG.

Пульт целиком описан Project-документом: четыре дугообразных сектора вокруг
обычной круглой OK, пары CH/VOL и боковые клавиши. Форма каждой фигурной кнопки —
нормализованный список точек `props.points`. Подписи — обычные label; стрелки
D-pad — отдельные треугольные polygons, полностью независимые от шрифта.
Общий Project-стиль `screen:remote.arrow` задаёт им `#1b1b1b`. Декоративные
стрелки не имеют событий, CLICKABLE/CLICK_FOCUSABLE выключены; состояние
DISABLED исключает их из стандартного LVGL keyboard focus traversal без
изменения вида, поскольку disabled-стилей у этих фигур нет.
Код [генератора Project](../examples/windows_player/tools/graphics_gallery.mjs)
только готовит JSON-данные: контуры секторов, полукруглых рокеров и шестигранных
клавиш. MCP может передать любой другой допустимый контур, не вызывая генератор
и не пересобирая приложение. Дуги и четыре скругления каждого сектора представлены 46 точками.
Зазор около 6 px имеет постоянную ширину у внешнего и внутреннего края;
внешний радиус 154 px, внутренний 78 px, диаметр OK 132 px и радиальный зазор
12 px. Углы имеют fillet около 6 px, подготовленный генератором. Никакой
отдельной C++-функции «сектор пульта» нет.

Общий optional-компонент
[ui:polygon_button](../examples/common/polygon_button/polygon_button.cpp)
(`id=514`, `abi=polygon-1`) не знает названий кнопок, углов, направлений, радиусов
и действий этого пульта. В C++ только замкнутый polygon path, обычный LVGL button
класс и `ADV_HITTEST` того же пути. Каталог
[catalog.json](../examples/common/polygon_button/catalog.json) публикует метод
`points`, границы 3..128 точек и координаты 0..1000 по обеим осям. Перед
выделением PointSpan storage native-handler проверяет эти границы; общий SDK
хранит точки до уничтожения экземпляра/замены успешного биндинга. Ширина и
высота объекта масштабируют один список точек одновременно для draw/hit-test.

Заливка явно even-odd; hit-test использует тот же even-odd алгоритм, включая
вогнутые и пересекающиеся контуры. Граница/обводка входят в активную область с
допуском `max(0.5 px, border_width/2)`, ограниченную прямоугольными границами
LVGL-объекта. Пустые части этого прямоугольника не нажимаются. Это штатная
точка расширения LVGL: после проверки object bounds движок вызывает
`LV_EVENT_HIT_TEST`, когда включён `ADV_HITTEST` — см.
[lv_obj_hit_test v9.6.0](https://github.com/lvgl/lvgl/blob/v9.6.0/src/core/lv_obj_pos.c).
Это настоящий LVGL pointer, а не прямоугольная кнопка под SVG или отдельный
движок UI-событий. `clicked`, `long_pressed`, обычные PRESSED/DISABLED/FOCUS_KEY states
и события MCP идут существующим engine.

MAIN `bg_color/bg_opa`, `border_color/border_width/border_opa` управляют фигурой;
стили состояния читаются штатно. `outline_width/color/opa` рисуют фокус по тому
же контуру вместо border, с шириной `max(border_width, outline_width)`; фокус
не расширяет hit-area. `outline_pad` не выполняет geometric offset. Полигон
задаёт фон и hit-area, но **не является clip-mask для произвольных потомков**:
дочерние надписи размещаются внутри фигуры самим Project и не кликабельны.
Радиус, тень и фон-картинка обычной прямоугольной кнопки не превращаются этим
минимальным компонентом в эффекты произвольного SVG.

OK/STOP управляют `demo.running`; +1/+10/СБРОС вызывают `demo.step`/`demo.reset`,
число нажатий приходит из `demo.clicks`; мини-дуга и цифры скорости связаны с
`demo.speed.kmh`. Конкретные назначения CH/VOL/HOME/MENU/BACK в этой демке тоже
заданы обычными событиями документа. Маленькая декоративная дуга убрана; скорость
остаётся обычным текстом с биндингом. Агент может менять point-list, размеры,
стили, подписи и actions через MCP. Статусбар получает реальный адрес viewer
и имя MCP из `host.connection.site`/`mcp`; порты не зашиты в Project.

В Настройках остались выбор схемы и обычные demo-биндинги: генератор, уровень
и счётчик. Параметров LLM, поля ключа, чата и источников assistant.* в демке нет.
Внешний [Designer на SPLA](readme_maui_designer_ru.md) работает с этим
приложением через прямой API, каталог данных и поток кадров. `/viewer` показывает
настоящий LVGL и принимает указатель, `/editor/` открывает общий редактор проекта.

Основные image-образцы — штатные `image`-узлы нашего ABI, использующие штатные
LVGL декодеры. BMP и BIN открываются через штатный memory filesystem. SVG
проходит настоящий LVGL SVG parser/vector renderer; растровой подмены SVG нет.
Ресурсы этой демонстрации пока регистрируются C++-кодом, их имена появляются
в capabilities. Это не реализация inline/URI ресурсов внутри Project.

Небольшой зарегистрированный `demo:graphics_sample` — **наш Windows-only
native-пример**, не штатный универсальный canvas/path ABI. Методы `mode` и
`progress` опубликованы общим metadata каталогом. Он использует стандартные
LVGL vector, line, Canvas и GIF API; геометрия сравнительной кривой фиксирована
в демонстрационном коде. Маркер связан с автономным `demo.speed.kmh` обычным
биндингом. GIF имеет собственный LVGL timer и продолжает работать при паузе
генератора. Cached raster обновляет tint при смене схемы.

Явные флаги [Windows lv_conf.h](../examples/windows_player/lv_conf.h):

| Флаг | Значение / назначение |
|---|---|
| `LV_USE_FLOAT`, `LV_USE_MATRIX`, `LV_USE_VECTOR_GRAPHIC` | 1, геометрия и Vector API |
| `LV_USE_THORVG`, `LV_USE_THORVG_INTERNAL` | 1, уже поставляемый LVGL software vector renderer |
| `LV_DRAW_THREAD_STACK_SIZE` | 32 КиБ, обязательный минимум этой LVGL-конфигурации с ThorVG |
| `LV_USE_SVG` | 1, SVG parser/decoder |
| `LV_USE_LODEPNG`, `LV_USE_TJPGD`, `LV_USE_BMP`, `LV_USE_GIF` | 1, bundled декодеры/анимация |
| `LV_USE_FS_MEMFS`, `LV_FS_MEMFS_LETTER` | 1 / M, чтение embedded BMP/BIN как файлов |

BIN decoder относится к обычной image-подсистеме LVGL; BIN — её существующий
формат, не новый формат NaCBORUIforLVGL. Дополнительно CMake включает сборку
встроенного ThorVG. Внешние libjpeg/WebP/FFmpeg и Lottie не добавлялись. Эти
Windows-настройки не перенесены в прошивку МК.

## Предложение для ресурсов МК: два источника, существующие форматы LVGL

Это направление обсуждения, **ещё не принятая и не реализованная схема Project**.
Логически достаточно двух способов дать байты одному LVGL image/GIF/SVG пути:

1. Встроенный бинарный ресурс: CBOR byte string с уже поддерживаемым форматом
   файла/изображения. При JSON-представлении преобразование бинарных данных
   решает общий кодек. Это не массив декоративных пиксельных команд и не новый
   формат картинок.
2. Ссылка на ресурс, например `fs://hand.gif`. URI раскрывает приложение:
   предоставляет разрешённые байты или путь зарегистрированного LVGL filesystem.
   Строка не означает автоматический доступ к произвольному файлу, HTTP URL
   или памяти. URI/provider и время жизни принадлежат приложению.

Сам рисунок можно выбирать по задаче: LVGL BIN для подготовленных пикселей,
PNG для lossless/alpha, JPEG для фотографий без alpha, GIF для простой анимации,
SVG для масштабируемой геометрии только при включённом vector-профиле. Формат
не должен создавать второй renderer рядом с LVGL.

Для будущего каталога ресурсов полезны имя/назначение, формат, ширина/высота,
размер encoded bytes, alpha, animated/frame count и информация о доступных
декодерах. Декодированная площадь и рабочая память оцениваются отдельно от
размера файла. До выделения памяти нужно проверять пределы bytes, размеров,
кадров/операций и глубины SVG. Inline bytes живут не меньше читающего их
LVGL-объекта; URI-кэш имеет явный общий бюджет и освобождение. Все ресурсы
раскрываются одним provider, независимо от того, пришли они из inline или URI.

В этой задаче ResourceURI/inline Project schema не добавлена: Windows-галерея
доказывает возможности и цену путей LVGL, а её compiled resources — временный
способ показать их владельцу. Выбор базовых MCU-флагов остаётся отдельным
решением после просмотра и измерений на целевой плате.

### Запуск, отключение и фактическая приёмка галереи

`npm run player:graphics` открывает самостоятельную графическую Windows-демонстрацию
(профиль `graphics`); системная демонстрация остаётся отдельным профилем. Для повторяемой приёмки без оконного ввода:

```powershell
node examples/windows_player/test-graphics.mjs <build>/Release/nacborui_player.exe
```

CMake-профиль `LVGL_CBOR_GRAPHICS_GALLERY` по умолчанию ON. Значение
`-DLVGL_CBOR_GRAPHICS_GALLERY=OFF` исключает gallery registration/resources/source
и тяжёлые Windows decoder/vector флаги; обычный `demo.json` остаётся доступен.
`LVGL_CBOR_HAS_GRAPHICS_GALLERY` — внутренняя compile definition, согласующая
`lv_conf.h` с этим выбором для LVGL и приложения. Отдельные декодеры по-прежнему
являются стандартными LVGL flags; полный gallery Project ожидает полный набор
своих образцов и сообщает ошибку при недоступном декодере. Это переключение
профиля сборки, не скрытая загрузка движка из CBOR.

Текущая приёмка разделённого профиля выполняется
[test-graphics.mjs](../examples/windows_player/test-graphics.mjs): настоящий скрытый
Win32/LVGL экземпляр и native NaWServer. Прежняя версия проверки использовала
удалённый посредник MCP и требует обновления; перечисленные ниже результаты
относятся к датированной приёмке до его удаления. Тогда проверялись декодированные
пиксели всех образцов, одинаковый checkerboard, прозрачные углы PNG/ARGB/A8,
точное совпадение BIN/RAW, независимая GIF-анимация, схемы и обычные события
пульта. Пустой холст дополняется через MCP `preview_project`; новая кнопка
отправляет штатное действие и обновляет подпись биндингом. Это проверка
работоспособности Windows-профиля, не FPS-бенчмарк или аппаратная приёмка S3.

Приёмка 2026-11-08 прошла на настоящем скрытом Win32/LVGL экземпляре:

- 12 растровых и 7 векторных образцов имеют реальные decoded/rasterized pixels;
  обе страницы целиком помещаются в 1280×800 между статусбаром и меню
  (76 и 49 явных узлов соответственно), без прокрутки;
- checkerboard одинаков у всех 19 образцов; непрозрачные RAW/BIN/JPEG/BMP/I4
  закрывают его своими пикселями, прозрачные углы PNG/ARGB/A8 показывают его;
- настоящий BIN и RAW RGB565: **0 отличающихся пикселей**; GIF при остановленном
  генераторе изменил сотни пикселей между двумя кадрами;
- обычные события пульта выполнены через настоящий stdio MCP → native
  NaWServer → DataRegistry/runtime; reset/+1/+10 дали счётчик 11,
  STOP/OK изменили источник и CHECKED-состояние центральной кнопки;
- HTTP pointer через `/api/view/input` подтвердил пять пустых углов/зазор
  без событий, PRESSED и действие внутри сектора. MCP поменял `points` того же
  узла с сектора на треугольник: прежняя внутренняя точка перестала нажиматься,
  новая внутренняя точка сработала; `send_event` сохранил то же действие.
  Изменённые через MCP FOCUS_KEY/styleRules дали видимый контур по треугольнику;
- исходный холст содержал один пустой root; `preview_project` через MCP добавил
  обычную кнопку +7 и подпись с биндингом, её event изменил счётчик до 18;
  чтение сохранённого Project подтвердило, что preview не сохранил правки;
- четыре схемы применились, все подписи остались видимы; password inspect
  вернул `[redacted]`; `bindingErrors`/`queueDropped` равны нулю, stderr пуст;
- процесс оставался скрытым и завершился штатно. Мышь, клавиатура и S3
  для этой проверки не использовались.

Просмотрены реальные raster-cream, vector-dark, controller-dark,
controller-pressed, controller-mcp-triangle и settings-dark снимки; по ним исправлены растягивание последнего образца и длинная подпись GIF.
Измерения и кадры лежат в ignored `local/windows-graphics-gallery`. Это проверка
нового разделённого graphics Project; прежняя приёмка единой страницы не
используется вместо неё. Сетевой ответ внешней модели и работоспособность её
провайдера этим graphics-тестом не проверяются.
