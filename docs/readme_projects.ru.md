# Проект: редактор, сервис прошивки и API

Решение владельца от 2026-10-22. Проект — общая единица открытия и сохранения: именованные экраны, общие именованные стили и описание проекта. Редактор остаётся универсальным; конкретные нативные компоненты приходят из каталога прошивки.

Дополнение 2026-10-23: экран можно вставлять в контейнер другого экрана вместе с его собственными биндингами и событиями. Начальная страница, допустимые переходы и политика хранения задаются обычными метаданными узла; см. [вложенные страницы](readme_page_composition.ru.md).

## Возврат из предпросмотра на главный экран МК

В верхней строке редактора доступна выделенная иконка домика **Главный экран МК**. Она заново получает сохранённый `manifest.entry` из ProjectService и показывает его существующей командой `show`, как при обычной загрузке приложения. Стартовый экран из несохранённого браузерного черновика для этого не используется. Это переключение дисплея: файлы проекта, настройки и локальные правки не сбрасываются; текущий раздел редактора остаётся открытым. Подсказка доступна при наведении, а в офлайне и во время операции проекта кнопка недоступна.

Выбор страницы в редакторе не меняет экран МК даже при включённом **Автоприменении**. Только правки выбранной страницы автоматически отправляют предпросмотр; переключение раздела, подключение, чтение проекта и выбор режима просмотра ничего не отправляют. Очередь ещё не отправленных правок отменяется при уходе со страницы или смене режима. Уже начатую операцию отменить на устройстве нельзя.

Кнопка **Посмотреть на МК** явно показывает выбранную страницу в режиме **Отдельно** или **В контейнере: …**. Режим общий для браузерного и аппаратного предпросмотра; места вставки берутся из графа проекта. Сохранённый проект и его стартовый экран не меняются. Для возврата к сохранённому стартовому экрану используйте домик.

## Изменения проекта извне без перезагрузки браузера

После **Открыть с МК** или успешного **Сохранить на МК** редактор следит за ревизией сохранённого проекта в текущем подключении. После успешного сохранения или сброса через API адаптер отправляет всем клиентам существующего `/ws` бинарное CBOR-событие `{v:1,event:"project_changed",revision:"…"}`. Событие не является ACK команды: у него нет `id` и `ok`. Неудачная операция, неизменная ревизия, preview и show уведомления об изменении хранилища не отправляют.

По событию редактор обновляет сведения ProjectService и читает целый проект только при другой ревизии. Периодического опроса проекта нет. После открытия/восстановления WS ревизия сверяется один раз, чтобы подхватить пропущенные за время разрыва изменения. События, пришедшие во время чтения, объединяются с последующей сверкой; последнее изменение не теряется. Изменения, сохранённые другим клиентом API, появляются без перезагрузки страницы. Браузер использует общий `ProjectClient`, и обращается к тому же API МК. Опрос INFO/capabilities соединения остаётся независимой диагностикой связи и не запускает опрос проекта.

Поддержка объявляется в `capabilities.project.events:["project_changed"]`. Для автоматического подхвата нужна соответствующая прошивка; для старой редактор показывает это ограничение. WS-уведомление — сигнал перечитать сохранённый документ, а не отдельное хранилище или поток патчей. Передача использует существующую ограниченную очередь NaWServer; отказ постановки логируется, собственной очереди повторов нет. Ручное обновление сведений остаётся доступным.

При автоматическом обновлении сохраняются выбранная страница, узел и именованный стиль, если они ещё существуют. Удалённый узел заменяется выбором корня, удалённая страница — стартовой страницей проекта. Размер просмотра берётся из обновлённого `screen.size`. Это чтение не сохраняет проект и не включает предпросмотр на LCD, даже при включённом автоприменении.

Локальные правки приостанавливают автоматическую замену. Если тем временем пришло уведомление об изменении ревизии МК, на странице **Проект** появляется сообщение о конфликте. Черновик остаётся в браузере; его можно экспортировать, затем явно открыть проект с МК. Сохранение по старой ревизии по-прежнему отвергается устройством. Если вернуть локальный документ к исходному состоянию, редактор снова сверит обнаруженную внешнюю ревизию. Правка во время скачивания тоже защищена от замены поздним ответом.

Само подключение не открывает проект. Открытие другого файла, явное переподключение, смена адреса или обнаруженный перезапуск МК прекращают слежение; для нового сеанса нужно снова открыть или сохранить проект. Краткая потеря сети без перезапуска не сбрасывает привязку. Несохранённый `preview_project` не меняет ревизию хранилища и в редактор автоматически не переносится.

## Документ и файл

Авторский JSON:

```json
{
  "format": "lvgl-project-1",
  "manifest": {
    "id": "panel",
    "name": "Панель",
    "entry": "main",
    "requirements": {"screenABI": "<screen fingerprint>", "styleABI": "<style fingerprint>"}
  },
  "screens": {"main": {"format": "lvgl-screen-draft-1", "id": "main", "name": "Главный экран", "size": {"width":800,"height":480}, "styles": {}, "root": {"id":"root","type":"obj","props":{},"style":{},"children":[]}}},
  "styles": {"accent": {"scope":"global","name":"accent","props":{"text_color":"#22cc88"},"attach":false}}
}
```

Настоящие fingerprints берутся из кодеков/возможностей прошивки; пример выше показывает форму. Общий стиль используется узлом через `styles:[{ref:"global:accent"}]`. Экранные стили и локальные свойства остаются внутри документа экрана. Стартовый экран задаётся `manifest.entry`. Необязательное `description` хранит описание проекта.

`packages/project-codec` проверяет проект целиком, ссылки на общие стили, тождество имён, циклы copy/merge и возможности устройства. Порядок общих стилей рассчитывается на ПК. JSON сохраняет авторскую запись; CBOR содержит бинарный manifest и карты именованных CBOR-пакетов экранов/стилей. Существующие style ABI v2 и screen ABI v3 сохраняются. Двусторонние кодеки возвращают редактируемый канонический документ. Проект не является JSON-текстом, который пришлось бы разбирать на МК.

Ресурсы прошивки (шрифты, изображения, нативные реализации) разрешаются через существующие реестры. Упаковка самих файлов ресурсов и шаблоны композиционных компонентов пока не добавлены. Привязки и события входят в узлы экранов как `bindings`/`events` и сохраняются вместе с целым проектом. Текущие значения датчиков и настройки рабочего окна редактора в проект не входят.

## Внутри прошивки

```cpp
// PROGMEM/const-пакет; исходный массив живёт дольше сервиса.
lvgl_cbor::ConstProjectSource base(project_cbor, sizeof(project_cbor));
lvgl_cbor::MemoryProjectStore changes;
lvgl_cbor::DataRegistry data; // Зарегистрировать источники/действия до load_screen.
lvgl_cbor::ProjectService projects(base, &changes, {}, {},
                                  resources, resource_count, &widget_registry, {}, &data);
std::string error;
if (!projects.begin(error)) { /* сообщить об ошибке конфигурации/хранилища */ }

// В LVGL-контексте приложения. Источник и общие стили выбираются внутри сервиса.
lvgl_cbor::ScreenReply reply;
projects.load_screen("main", reply);
```

`ProjectService` принадлежит приложению. `load_screen(name,reply)` читает итоговый экран, создаёт отдельный контекст общих стилей, исполняет экран и активирует его. При ошибке создания прежний экземпляр остаётся. `preview(whole_project,screen,reply)` создаёт такой же изолированный экземпляр из черновика, не меняя сохранённый проект. Все вызовы LVGL и уничтожение сервиса выполняются в UI-контексте. Чтение/изменение хранилища сериализуется внутри сервиса; оно не вызывает LVGL.

Один принадлежащий приложению `DataRegistry` передаётся последним необязательным аргументом. Он используется и при именованной загрузке, и при предпросмотре; заменённый экран снимает свои подписки и отменяет отложенные события. В UI-цикле приложение публикует подтверждённые значения и вызывает `data.flush()`. Отдельного загрузчика, проекта или хранилища для биндингов нет. [Схемы, регистрация и события](readme_bindings.ru.md).

`read_screen/read_style`, `write_screen/write_style`, `remove`, `reset` доступны непосредственно коду прошивки. `save_project` публикует проект целиком одной операцией хранилища. Исполнимые документы должны быть скомпилированы общими кодеками; МК проверяет оболочку, идентичность, границы, ABI и политику хранения, но не строит дерево команд и не вычисляет порядок setter-ов.

Сохранение не изменяет текущую картинку. Для отображения сохранённого состояния приложение отдельно вызывает `load_screen`. Выбор стартового экрана тоже не переключает дисплей немедленно.

## База и один слой изменений

`ProjectSource` задаёт базу, `ProjectStore*` — один необязательный слой изменений. По имени сначала используется изменение, затем база. Изменение заменяет целый экран/стиль. Отметка удаления скрывает базовую запись; сброс перекрытия возвращает её. Само тело базового пакета в PROGMEM не копируется в RAM: индекс держит представления и имена. Файловая база текущего адаптера читается целиком в ограниченный буфер.

Варианты конфигурации находятся в коде приложения, а не в браузере:

```cpp
lvgl_cbor::ConstProjectSource base(rom_bytes, rom_length);
// Или: FileProjectSource base("/sdcard/ui/base.cbor");

lvgl_cbor::MemoryProjectStore changes; // до перезапуска
// Или: FileProjectStore changes("/littlefs/ui/changes");
// Или: FileProjectStore changes("/sdcard/ui/changes");
// Или: nullptr вместо &changes — только чтение.

lvgl_cbor::ProjectPolicy fixed{true, false, false}; // replace, add, remove
```

Приложение монтирует FS/SD, создаёт каталог и выбирает пути до `begin()`. Адаптер не содержит драйвера SD, не выбирает раздел и не перенастраивает железо. Можно реализовать другие источники/хранилища через те же интерфейсы.

`FileProjectStore(prefix)` использует `prefix.0` и `prefix.1`: номер поколения, размер, контрольную сумму, flush/sync. Сначала записывается неактивное поколение. При оборванной/повреждённой новой записи загрузчик выбирает предыдущее целое. Ошибки открытия/чтения не маскируются под отсутствие изменений. Повреждение обеих записей и несовпадение отпечатка базы дают явную ошибку. Физические гарантии конкретного носителя/драйвера требуют аппаратной проверки.

На носителе хранится разница с базой: изменённые документы, удаления, описание и порядок. При экспорте получается полное итоговое содержимое проекта. Изменения привязаны к отпечатку базы. Полностью гибкая политика допускает загрузку другого ID проекта в тот же слот, с сохранением возможности возврата к базе. Фиксированная политика сохраняет идентичность и разрешённый набор.

## Редактор

**«Проект»** — первая отдельная страница редактора. Команды **«Открыть с МК»** и **«Сохранить на МК»** находятся в самом верхнем блоке; рядом постоянно видны носитель записи и срок хранения. Ниже — сохранённый проект МК, права, база и изменения; дополнительные носители/каталог/лимиты раскрываются в том же блоке. Следующие зоны — настройки рабочей копии/стартовый экран и целый файл JSON/CBOR. **«Экраны»** открывают управление экранами; под ними — редакторы отдельных экранов. **«Стили»** открывают общие стили проекта. **«Устройство»** содержит технические сведения о плате. Управление проектом не закреплено в остальных редакторах. Файловые операции проекта используют тот же отключаемый модуль `DocumentFiles`, что и документы экранов/стилей.

На странице **«Стили»** список именованных стилей расположен слева, свойства выбранного стиля — рядом; верхнего выпадающего выбора больше нет. Добавление, копирование и удаление доступны кнопками и через ПКМ. Используемый стиль нельзя удалить до снятия ссылок; переименование обновляет ссылки узлов, общих и экранных определений.

**ПКМ по узлу дерева экрана** выбирает этот узел и открывает общие команды: добавить стандартный/нативный компонент, прикрепить или снять именованный стиль, переместить и удалить. Выбор компонентов использует тот же действующий каталог, что и обычный список. Меню поддерживает Escape, стрелки, Enter и Shift+F10. **Drag-and-drop** переносит узел до/после соседа либо внутрь контейнера obj/button; место вставки подсвечивается. Корень не переносится, циклы и перенос родителя в собственного потомка отклоняются. Изменение остаётся правкой черновика, с обычными правилами предпросмотра и явного сохранения.

- «Открыть с МК» читает сохранённый проект в рабочую копию редактора и не меняет дисплей.
- «Посмотреть на МК» показывает полный снимок черновика и не сохраняет его. Автоприменение делает только этот шаг.
- «Сохранить на МК» явно записывает проект в настроенный слой изменений, без переключения дисплея. Для RAM интерфейс сообщает: до перезапуска.
- «Сохранить файл» выгружает целый проект на ПК.

Подключение запрашивает возможности и сведения о сервисе; оно не отправляет черновик и не заменяет его проектом МК. Черновик восстанавливается в localStorage. Старые раздельные черновики экранов/стиля мигрируют в начальный проект. HTML с S3 и локальный сайт используют один контракт API, но имеют разные браузерные хранилища.

При открытии с МК повторно запрашиваются каталог компонентов, ресурсы и лимиты прошивки. Страница проекта показывает разрешённые сервисом операции, базу и слой изменений (`kind`, `location`, `persistent`, `writable`, `state`), а также объявленный приложением список `media`. `not-configured` означает отсутствие настройки драйвера/носителя в приложении; `unknown` — отсутствие сведений. Эти состояния не доказывают отсутствие физической SD-карты. Пустой список носителей означает, что прошивка его не объявила. Только чтение на МК не мешает редактировать рабочую копию и выгружать её в файл.

`storage_info()` источника/хранилища может сообщать актуальное состояние приложения. Файловые адаптеры принимают вторым аргументом имя носителя, например `FileProjectStore("/sdcard/ui/changes", "SD")`. Дополнительный список носителей передаётся последним аргументом конструктора сервиса. Сервис не сканирует аппаратные интерфейсы и не выбирает носитель вместо прошивки.

## Необязательный HTTP API

Адаптер `integrations/nawserver/project_api.*` использует `ProjectService`. Приложение вызывает `process()` в UI-задаче. HTTP не выполняет LVGL. Все операции идут через `/api/project?action=...`:

| Метод/action | Действие |
|---|---|
| GET `info` | Проект, revision/baseRevision, список имён, носитель, постоянство и разрешённые операции |
| GET `read` | Полный сохранённый CBOR-проект; `X-Project-Revision` соответствует этим байтам |
| GET `screen`/`style`, `name` | Один именованный CBOR-документ |
| POST `begin` | CBOR: intent=`preview`/`save`, size, revision, screen; возврат token/chunkBytes |
| POST `chunk`, token/offset | Следующая часть пакета, максимум 2048 байт |
| POST `finish`, token | Проверка комплектности; отдельное сохранение либо очередь предпросмотра |
| POST `cancel`, token | Отмена незавершённой передачи |
| POST `show` | CBOR `{screen}`: показать сохранённый экран по имени |
| POST `reset` | CBOR `{kind,name,revision}`: сброс перекрытия; пустые kind/name сбрасывают все изменения |

Транспорт передаёт целый проект, разбитый на ограниченные части, потому что NaWServer ограничивает тело запроса 4096 байтами. Это не патчи объектов. Неполная загрузка и отмена до `finish` не публикуются. Одновременно принимается одна передача, срок бездействия — 30 секунд. Проверка revision при сохранении отклоняет устаревшего редактора с HTTP 409. Долгий предпросмотр ограничен ожиданием UI-задачи; результат следует перепроверить при тайм-ауте уже начавшегося исполнения.

Обычный клиентский `timeout` — 15 секунд. Только `finish` явного сохранения использует отдельный `saveTimeout`: по умолчанию 60 секунд, настраивается в конструкторе `ProjectClient`. Запись каталога и нескольких файлов SPIFFS может занимать дольше передачи пакета. Сохранение выполняется в HTTP-задаче; серверное ожидание UI-задачи в 10 секунд относится к предпросмотру/показу, а не к записи. Истечение клиентского ожидания или разрыв связи не отменяет уже начавшийся commit; его результат следует сверить по фактическому `revision` перед повторной записью.

Общий `packages/project-codec/client.js` используется браузером и другими клиентами API. Сохранение отдельного документа через клиент также выполняется полной транзакцией проекта с проверкой revision и общей компиляцией.

## Модульность и MCP

ProjectService, кодеки и HTTP-адаптеры остаются общими. Браузер не исполняет
дополнительный сервер и не записывает проект при подключении. API передаёт
ограниченные CBOR-транзакции в существующий исполнитель.

Designer по умолчанию работает с HTTP/CBOR API устройства напрямую.
В Windows отдельно доступны [встроенный MCP проигрывателя и внешний MCP
Designer](readme_mcp.ru.md).
