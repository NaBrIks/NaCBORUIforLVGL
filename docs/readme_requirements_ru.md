# Требования

Основание: обсуждения владельца 2026-10-20 и 2026-10-21.

## Подтверждённое направление

- Название проекта: **NaCBORUIforLVGL**. Имя репозитория: `NaCBORUIforLVGL`; имя локальной папки произвольное.
- Загружать совершенно новые экраны во время работы устройства без перепрошивки.
- Поддержать привязки элементов интерфейса к данным приложения.
- Сократить ручную установку свойств/стилей и поддержать динамическую смену дизайна; базовые биндинги остаются необходимой частью направления.
- Предусмотреть постоянные привязки, продолжающие обработку при другом экране, и убираемые экранные привязки.
- При включении до получения значения показывать `--`, не подставлять ноль.
- Передавать описание в CBOR с символьными именами UTF-8 для сущностей и прикладных данных. По уточнению 2026-10-21 для методов стилей разрешены числовые инструкции с отдельной версией индексации.
- Собственный исполнитель превращает описание в объекты LVGL; CBOR-декодер не заменяет этот исполнитель.
- Текущий этап включает общий сервис стилей, динамические экраны/компоненты, двусторонние кодеки, веб-стенд S3 и разрешённую владельцем 2026-10-22 реализацию данных/событий. Возможности редактора уточняются по данным прошивки.

## Обсуждаемые варианты

Для первого опыта: JSON как авторский исходник, отдельный переиспользуемый JS-кодек, TinyCBOR на ESP32-S3, LVGL 9.6.0 и контракт style ABI v1. Общая схема документа экранов ещё не утверждена.

[Модель привязок](readme_bindings_ru.md): фиксированный именованный реестр типизированных источников/действий, обработчик доменных событий, ограниченные выражения и уведомление зависимых привязок. Полный скриптовый язык не используется; принятый контракт выражений фиксирует границы первой версии.

## Требует определения

Схема и версия документа; виджеты и стили; типы данных и форматирование биндингов; действия; ресурсы; лимиты; владение памятью; обработка ошибок; замена и выгрузка экранов; поддерживаемые платформы; лицензия собственного кода.

## Уточнения владельца 2026-10-22

Разрабатывается **общий редактор**, пригодный для разных приложений и компонентов. Радар, спидометр и другие примеры не определяют его интерфейс. Для конкретного пользовательского компонента запрещены специальные кнопки, формы, условия по имени/ID и привилегированное размещение. Список типов, названия, ID методов, формы аргументов и начальные габариты поступают из каталога платы и обрабатываются общими механизмами. Добавление нативного компонента с поддерживаемыми формами аргументов требует его регистрации и метаданных, без изменений редактора. Если нужна новая форма аргумента, расширяется общий механизм схем и полей. Реализации и данные демонстрационных компонентов остаются в отдельных отключаемых модулях примеров.

Код должен быть максимально модульным. Общие правила проверок и преобразований не дублируются. App.vue отвечает за представление и сборку компонентов. Удаление дублирования с сохранением поведения приветствуется.

Статические глобальные, динамические глобальные, экранные и локальные стили обслуживаются общим сервисом. При удалении экрана ресурсы освобождаются после объектов; кэш опционален. Исследование памяти и автоматические политики пока не выполняются.

Предложения владельца сначала оцениваются по преимуществам, недостаткам, применимости и распространённости. Предложенный механизм не считается прямым обязательным указанием, когда владелец обозначил его как вариант.
