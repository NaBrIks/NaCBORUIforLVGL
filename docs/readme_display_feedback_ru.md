# Кадр настоящего LVGL и граница MCP

Windows target предоставляет `/api/view/frame` через существующий NaWServer.
Веб-редактор и NativeViewer читают BMP непосредственно у target; это кадр LVGL,
а не снимок рабочего стола или браузерная перерисовка JSON. Получение кадра не
сохраняет проект и не переключает страницу.

## Снимок в MCP

В Designer при прямом подключении `get_display_frame` использует последний
завершённый кадр предпросмотра и кодирует его в PNG на компьютере.
`fresh:true` ждёт следующего завершённого обновления, `afterScene` — кадра
после смены сцены. При отсутствии предпросмотра используется запрос кадра
у устройства. Внешний локальный endpoint Designer в Windows использует тот же
путь. См. [снимок через MCP Designer](readme_maui_designer_ru.md#снимок-через-mcp-designer).

Опциональный [MCP Windows-проигрывателя](readme_windows_native_mcp_ru.md#изображение-и-бюджеты)
снимает кадр LVGL и кодирует PNG внутри проигрывателя.

## Порции LVF2 на S3

Устройство объявляет `native_view_packet_version: 2` в `/api/info`.
Designer и NativeViewer запрашивают `GET /api/view/frame?packets=2&since=<ревизия>`.
Пустой ответ 204 означает, что новых зон нет. Полный кадр нужен при первом
запросе, смене сцены или потере истории. Старые BMP и LVF1 остаются доступны.

В DIRECT история собирается по прямоугольникам LVGL flush. Удалённые друг от
друга зоны передаются отдельными порциями. Две зоны объединяются только если
охватывающий прямоугольник не дороже по пикселям, чем исходные две. Размер
истории ограничен 192 прямоугольниками, в плане ответа до 12 зон. В FULL LVGL
сообщает перерисовку всего экрана, поэтому каждый изменённый кадр остаётся полным.
В DIRECT буферы по-прежнему полноразмерные. LVGL обновляет только нужные области,
а RGB-контроллер продолжает развёртку всего экрана. DIRECT — режим новой
конфигурации S3, сохранённый выбор устройства имеет приоритет.

В разделе «Устройство → Дисплей» есть RLE и «Буфер порции». То же задаётся
полями `rle` и `rleBuffer` в CBOR-запросе `POST /api/display/config`.
Настройки применяются после перезапуска. При RLE и включённом буфере кодировщик
использует 4 КиБ, сравнивает размеры для каждой порции и выбирает RAW, если
RLE не уменьшает данные. С выключенным буфером RLE пишет в сетевой буфер
NaWServer и иногда может увеличить объём. Если RLE выключено, буфер порции
не выделяется. Используются рабочие framebuffer, без копии всего экрана.

Оба вида порций имеют 32-байтный заголовок little-endian. Первые 4 байта —
`LVF2`, затем три u32 — размер payload, ревизия, сцена, затем u16 —
x, y, ширина, высота, ширина и высота дисплея, формат (1 = RGB565LE), флаги.
Бит 0 отмечает последнюю порцию, бит 1 — RLE. RAW имеет точный размер payload.
RLE использует размер 0 и читается до заполнения заданного прямоугольника
(до 4096 распакованных байт). Младшие 7 бит токена задают число пикселей минус
один. Старший бит означает повтор следующего RGB565-слова. При нуле за токеном
идут буквальные RGB565-слова. Весь HTTP-поток заканчивается EOF, а флаг последней
порции позволяет клиенту отличить завершённое обновление от обрыва.
`X-Frame-Raw-Bytes` задаёт объём распакованных данных для прогресса.

## HTTP и WebSocket в Designer

S3 объявляет `native_view_ws: true`. В предпросмотре Designer можно переключить
HTTP / WS. HTTP использует прежний потоковый GET. WS держит соединение с
`/api/view/ws`. Designer передаёт последнюю применённую ревизию десятичным
числом, затем ждёт изменения. Одновременно активен один запрос. Сервер посылает
`begin,revision,scene,x,y,width,height,cropWidth,cropHeight,rawBytes,full`,
затем бинарные фрагменты тех же LVF2-порций и текстовый `end`.
`idle` завершает ожидание без изменений. При смене сцены сервер прекращает
формировать старые фрагменты и шлёт `cancel`. Клиент откатывает незавершённое
обновление и запрашивает полный кадр. До прихода новых порций на холсте
остаётся последний полностью принятый кадр. Уже переданные в транспорт байты могут
дойти до `cancel`.

Один клиент WS. На S3 ему доступен один управляемый сетевой блок в 4 КиБ.
В бинарный фрагмент входит до 4092 байт LVF2, в том числе несколько сжатых
порций. Приложение хранит один подготовленный фрагмент до освобождения
сетевого блока. HTTP и WS используют общий источник, кодировщик RLE
и ограничение на одну активную передачу кадра. Нажатия идут через прежний API.

Рядом с Progressive в одной строке всегда видны общий объём обновления,
обработанный объём и шкала. Для LVF2 это распакованные байты. 800×480 RGB565
занимает 768 000 распакованных байт. В DIRECT при передаче только часов или
других зон общий объём равен сумме их размеров. Фактический сетевой объём
при RLE меньше и определяется к концу передачи.

## Микроконтроллер

Формат Windows BMP не является обязательным форматом МК. Нужно явно объявлять
width, height, stride, формат и порядок байтов/битов, owned lifetime, пределы
bytes/pixels и поддержку capture. Нельзя угадывать формат по имени процессора
или возвращать кадр другого target при недоступности выбранного устройства.
На частичных draw buffers полный кадр может требовать дополнительной памяти
и перерисовки; это необходимо проверить на конкретной плате.
