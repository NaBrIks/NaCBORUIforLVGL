# Свежий кадр LVGL для агента

`get_display_frame({maxEdge:1024})` — readonly MCP-инструмент над существующим
`/api/view/frame` NaWServer. Он не сохраняет проект, не переключает страницу,
не эмулирует ввод и не делает снимок рабочего стола Windows.

Сейчас Windows endpoint возвращает BMP40/BI_RGB с32-битными BGRX-пикселями
XRGB8888. MCP-хост читает его с пределом bytes/pixels, уменьшает при необходимости
и кодирует PNG встроенным node:zlib. Нового HTTP-стека или сторонней image library
нет. PNG отправляется как MCP image content, рядом текстом — исходные/выходные
размеры и состояние композиции, прочитанное после кадра.

Встроенный агент передаёт картинку модели как image_url после ответов на все
инструменты текущего batch. Base64 не вставляется текстом в tool result или
журнал. Предыдущий кадр обратной связи удаляется из модельного контекста при
появлении нового; пользовательские референсы сохраняются. Каждая операция capture
явная, непрерывного потока для агента нет. Модель должна принимать изображения
по фактическому каталогу провайдера; для текстовой модели возвращается ошибка.

Пределы host: до2×1024×1024 пикселей,8 MiB пиксельных данных плюс BMP header,
сторона PNG до1024, PNG до1 MiB. Встроенный агент имеет более узкий image-бюджет
96 KiB на кадр и общий request-бюджет1 MiB: большой PNG отвергается с предложением
запросить меньший maxEdge. Байты не обрезаются. maxEdge уменьшает изображение
на хосте **после получения полного исходного кадра**, не снижает стоимость
самого capture или объём исходного BMP на устройстве.

## МК остаётся в родном формате

32-битный BMP — текущий Windows-источник, не обязательный wire-формат MCU.
Микроконтроллеру не нужен PNG encoder или разворачивание своего RGB565/монохромного
буфера в32 бита ради модели. Внешний host должен знать width,height,stride,
формат пикселей, порядок байтов/битов и кодировать PNG самостоятельно.

Host-кодек encodeRawFrame поддерживает также RGB565 little/big endian, однобитный
монохром MSB/LSB, RGB888, BGR888 и BGRX8888. Строки top-down, stride в байтах;
для mono1 определено0=чёрный,1=белый. Это обработка пикселей вне устройства; MCU capture endpoint
и формат его метаданных этим не объявляются реализованными. Новый raw wire-контракт
требует отдельной фиксации; нельзя угадывать stride, формат или считать данные
RGB888 по названию процессора.

Если полный framebuffer уже есть, по возможности использовать его с корректным
owned lifetime. На дисплее с частичными draw buffers получение полного кадра
может потребовать дополнительной памяти и перерисовки — отсутствие PNG на МК
эту цену не устраняет. Устройство должно явно объявлять поддержку capture и свои
лимиты. Неподдержанное устройство возвращает display_capture_unavailable, не чужой кадр.
Для MCU сначала выбирать ограниченную, вызываемую по запросу реализацию, а не
переносить Windows snapshot с многомегабайтным XRGB8888-буфером.

## Что проверено

Настоящий скрытый Windows LVGL → NaWServer BMP → stdio MCP PNG → multimodal
контекст mock-модели. Два последовательных кадра разных размеров, корректный
порядок tool replies, удаление старого feedback image, неизменённые биндинги/
события и сохранённый документ. Тестовый provider в памяти, сетевого mock-listener
нет. Реальная Qwen также получила кадр и перечислила визуальные проблемы своего
макета; это проверка связи, ещё не приёмка качества сложного дизайна.

[Системный контекст и проверка дизайна](readme_assistant_design_ru.md) ·
[MCP](readme_mcp_ru.md)

Проверки host-пикселей:13/13 (RGB565 LE/BE, mono1 MSB/LSB, stride/padding,
BMP orientation, resize, Full HD, точный2 Mi-pixel предел, повреждённые данные).
