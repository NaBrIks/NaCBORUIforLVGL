# Предложение: изображения внутри проекта и ссылки на ресурсы

Статус: направление владельца 2026-11-07; конкретный wire-контракт ещё не принят.
Ориентация — МК и декодеры самой LVGL. Собственный графический формат не нужен.

## Два источника, один интерфейс изображения

1. Inline: CBOR byte string с данными изображения плюс описание его формата.
   JSON-представлению нужен явный способ кодирования байтов, например base64;
   общие кодеки преобразуют его в CBOR bytes. По wire base64 не требуется.
2. Ссылка: зарегистрированное имя ресурса или URI, например fs://hand.gif.
   Приложение разрешает URI через заранее подключённый источник/драйвер.
   После разрешения renderer получает обычный источник изображения LVGL.

Конкретные ключи/номера в CBOR пока не фиксируются. В существующем screen ABI
image.src принимает имя уже зарегистрированного ресурса; inline bytes и fs://
ещё не являются поддержанным расширением проекта. Галерея показывает настоящие
LVGL декодеры на зарегистрированных C++ ресурсах и MEMFS, не выдаёт это за готовый
переносимый resource-upload API.

Ссылка не равна разрешению на произвольный доступ к файловой системе. Источники,
корень FS и доступные URI-схемы объявляет приложение. Для MCU нужен ограниченный
resolver и owned lifetime, без фонового сетевого загрузчика или второго image engine.

## Форматы выбираются по задаче

| Формат | Разумное применение | Цена и ограничения |
| --- | --- | --- |
| LVGL BIN / подготовленные native pixels | Предсказуемая загрузка UI, иконки, фоны | Размер определяется цветовым форматом; версия заголовка/endianness должны совпадать |
| PNG | Картинки и иконки с прозрачностью | Сжатое хранение; декодирование требует CPU/RAM |
| JPEG | Фотографии и пёстрые фоны | Нет alpha, есть потери; ограничения зависят от выбранного LVGL decoder |
| GIF | Простая кадровая анимация | Декодированный холст и состояние анимации расходуют RAM, даже при небольшом файле |
| SVG | Масштабируемые контуры/иконки | Поддерживаемое LVGL подмножество и векторный renderer; заметная программная цена |

Нет универсального «лучшего» формата. Статический сложный SVG для слабого МК часто
разумно подготовить в растр на ПК. Изменяемые линии, дуги и графики оставлять
геометрией LVGL; сглаженную кривую можно заранее дискретизировать.

## Что должен видеть MCP

Capabilities должны сообщать включённые decoder и URI-схемы, а каталог ресурсов —
имя/тип, формат, размеры, наличие alpha/анимации, длину и происхождение. Выдача
фильтруется/пагинируется как остальные каталоги. Описание не копирует сам payload
картинки в каждый discovery-ответ. Объявленные ресурсы приложения остаются отдельны
от динамических измерений DataRegistry.

## Память и жизненный цикл

До выделения проверить bytes, ширину/высоту, число пикселей, цветовой формат,
доступный decoder и бюджет распакованного изображения/кадра. Файл в несколько
килобайт способен потребовать большой декодированный буфер. Отдельно ограничить
анимации, cache и число одновременно используемых ресурсов.

Буфер inline должен жить не меньше всех объектов/decoder-cache, использующих его.
Смена проекта освобождает ресурсы после дочерних объектов; URI-кэш имеет явную
политику. Неподдержанный формат выдаёт ошибку/заглушку, не подменяется другой
картинкой. Проверки сначала выполняются Windows-демкой на настоящем LVGL, затем
на MCU с тем же форматом и фактическими лимитами.

См. [графику LVGL](../readme_graphics_ru.md).

## Подготовка изображений вне МК — уточнение 08.11.2026

Проверяем направление: преобразовывать выбранные изображения в поддерживаемый
LVGL BIN на ПК/в браузерном клиенте, затем в будущем тем же контрактом в Android.
На МК остаются общий resource resolver и загрузка native формата. Это план,
не реализованный upload API или встроенный конвертер студии.

Нужно закрепить версию BIN под целевую LVGL, цветовой формат, alpha, размеры,
stride и byte order; результат проверять настоящим LVGL, а не только браузером.
Не придумывать отдельный формат. Статические сложные изображения можно заранее
растрировать; динамические векторные контролы, подписи, области нажатия и события
должны остаться компонентами. Превращение всей страницы в картинку не выполняет
задачу описательного UI.

Для первоначальных модельных опытов использовать уже зарегистрированные ресурсы.
Изображение-референс отправляется модели для анализа, но не выдаётся за ресурс
прошивки. Конвертация и доставка новых assets — отдельная часть после принятия
контракта ресурсов, без второго HTTP-стека и без дублирования проектного кодека.
