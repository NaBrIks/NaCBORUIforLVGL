# Android: голосовой конструктор и проигрыватель LVGL

Дата: 2026-11-07. Статус: план по прямому поручению владельца; Android-приложение,
интеграции моделей и голосовой ввод пока не реализованы. Этот документ фиксирует
направление, этапы и вопросы проверки, а не обещает поддержку конкретного телефона
или провайдера.

## Основной сценарий

Пользователь говорит в микрофон, какой интерфейс хочет получить. Приложение
сохраняет редактируемый текст запроса, получает описание проекта от выбранной
модели, проверяет его общими кодеками и показывает результат на настоящем LVGL
прямо на телефоне. Уточнение голосом или текстом меняет тот же проект. Небольшой
редактор для ручной правки размеров, подписей и оформления — второстепенная
возможность, а не главный способ сборки экрана.

Телефон также может открыть существующий JSON/CBOR-проект. Подключение к МК
позволяет получить его реальные возможности и данные, примерить новый интерфейс
и отдельно сохранить его. Создание интерфейса не требует добавления модели в
прошивку МК.

## Один формат, кодеки и движок

```text
Голос -> распознанный текст -> редактируемое задание
                                  |
Фактический каталог МК ------------+--> выбранная модель -> Project JSON
Текущий проект и история правок ----+                           |
                                                      общая проверка
                                                             |
                              общие JSON <-> CBOR кодеки -> Project CBOR
                                                             |
                       общий ProjectService / ScreenRuntime / DataRegistry
                                                             |
                                                  настоящий LVGL на Android
                                                             |
                                  существующий API МК: preview / show / save
```

Основа — существующий C++ runtime, биндинги, события и проектный формат;
см. [Windows-проигрыватель](../readme_windows_player_ru.md). Отдельный Android
JSON-исполнитель, своя модель привязок или параллельные парсеры не планируются.
Модель выдаёт редактируемый проект, а не произвольный исполняемый код.

Windows Win32 backend нельзя перенести на Android без изменений. Android нужны
собственные адаптеры display/input, жизненного цикла приложения, времени,
файлов/ресурсов и связи с платформенной оболочкой. Сборка/линковка общего ядра
через NDK и мост с оболочкой — кандидат для прототипа, а не уже выбранная
реализация. Поворот, плотность пикселей, касания, пауза/возврат приложения и
владение LVGL-потоком проверяются отдельно. Шрифты Windows не переносятся.

Существующие общие кодеки написаны на JavaScript. В прототипе требуется выбрать
способ их упаковки/выполнения на Android и мост передачи CBOR в C++: например,
изолированный JS-контекст или платформа с подходящим JS-host. Конкретный host,
библиотека и размер зависимостей ещё не выбраны. Наличие Node.js в Windows-демке
не означает его обязательность на телефоне. Платформенные файловые адаптеры
нужно отделить от общей компиляции; писать второй кодек на Kotlin/C++ ради
Android не предлагается.

## Каталог для агента

Модель должна проектировать по доступным возможностям, а не угадывать их по
названиям. Источник истины — метаданные приложения/МК и общие контракты:

- разрешённые компоненты, их методы, состояния, стили, Flex/Grid и ограничения;
- реальные ресурсы: имена и типы шрифтов/изображений, размеры дисплея;
- источники данных и действия: стабильные имена, названия/описания, типы,
  вложенные поля, доступность записи, единицы и ограничения;
- способы навигации, вложенные страницы и политика удержания экземпляров;
- для временных рядов — форма серии, период/время, пропуски и предел хранения,
  когда это будет формализовано в общем реестре.

Нужное описание реестра должно приходить из одного общего API/MCP-каталога,
а не поддерживаться отдельным списком для Android. Предложенные расширения
метаданных и динамический lifecycle сначала согласуются в общем реестре.
Текущие возможности и границы описаны в [биндингах](../readme_bindings_ru.md)
и [MCP](../readme_mcp_ru.md).

Для небольших моделей не отправлять все контракты, документацию и текущие
значения целиком в каждый запрос. Предусмотреть компактный обзор групп,
последующий запрос нужных компонентов/ветвей данных и точные описания выбранных
методов. Фильтрация меняет объём контекста модели; финальная проверка всегда
использует полный соответствующий каталог. Число шагов получения описаний,
размер каждого ответа и общий бюджет запроса ограничиваются.

Текущие [режимы Designer](../readme_designer_connections_ru.md) используют
прямой API как основной путь. Профили MCP используют HTTP-клиент SPLA.

## Провайдеры и голос

OpenRouter — запрошенный кандидат подключения, а не единственный транспорт.
Граница провайдера должна позволять сменить модель и сервис, подключить другой
совместимый endpoint либо локально запущенную модель без переделки проекта,
рендерера и кодеков. Совместимость API, структурированного вывода, вызова
инструментов, streaming, timeout и отмены проверяется для выбранного endpoint;
одинаковый формат URL не доказывает одинаковое поведение моделей.

Распознавание речи — отдельная заменяемая возможность. Исследовать системное
распознавание Android, серверный и при подходящем устройстве локальный варианты.
Текстовый ввод остаётся доступен при отсутствии микрофона или распознавания.
Пользователь может исправить распознанный текст перед запросом и продолжить
работу текстом. Озвучивание ответа не требуется для первого результата.

Запуск модели непосредственно на телефоне — отдельное исследование по RAM,
скорости, нагреву, батарее, размеру модели и качеству генерации с каталогом.
Не обещать произвольную LLM на слабом телефоне. Если локальный inference
неподходящ, тот же сценарий использует внешний endpoint. Ключи провайдера не
входят в JSON/CBOR-проект, снимок capabilities или историю переписки; способ
их защищённого хранения выбирается вместе с Android-host.

## Проверка, просмотр и МК

1. Получить каталог целевого приложения/МК и сохранить его точный снимок с
   версией контрактов. Офлайн-снимок явно отличается от подтверждённых текущих
   возможностей устройства.
2. Передать модели задание, текущий проект и необходимые части каталога.
3. Проверить полученный Project JSON общими валидаторами: методы, ресурсы,
   типы привязок/действий, ссылки страниц и лимиты. Ошибки возвращаются в цикл
   исправления с ограничением попыток; невалидный проект не применяется.
4. Скомпилировать CBOR и показать на телефоне через общий runtime. Если Android
   не содержит нативного компонента МК или ресурса, это явно неполный просмотр;
   не выдавать похожую заглушку за точное воспроизведение компонента.
5. Перед отправкой на МК сверить актуальный каталог/контракты и перепроверить
   проект при изменении возможностей. Выполнить существующий preview, затем
   проверить ACK, состояние проекта/композиции, биндинги и ошибки.
6. Постоянное сохранение выполнять отдельной командой через существующий save
   с проверкой revision. Preview и открытие проекта сами по себе не сохраняют.
   Конфликт не затирается автоматической повторной записью.

Смена страницы, тест модели и подключение телефона не должны неявно переключать
дисплей МК. Отображение и хранение сохраняют уже принятые отдельные операции.
Нативные компоненты можно изменить через описание только в пределах открытых
параметров/методов; произвольная замена их C++-рисования через CBOR не обещается.

## История и воспроизводимость

Хранить редактируемый текст задания и уточнений, выбранный провайдер/модель,
принятый Project JSON, соответствующий CBOR и точный снимок capabilities,
по которому результат проверен. Черновой ответ модели и принятый проект
различаются. Каждое последующее изменение строится от определённого состояния
проекта; отмена/повтор и возобновление сессии не должны незаметно подменять
исходный вариант. Голосовая запись, если сохраняется, имеет отдельную политику
хранения; длительное хранение звука не является условием основного сценария.

Промежуточные примеры данных для просмотра отделяются от фактических измерений
МК. История разговора служит редактируемым контекстом, а не заменой сохранённого
документа и его версии. Старые сообщения не отправляются без ограничения:
при сокращении контекста точный текущий проект и каталог остаются доступными.

## Ресурсы и отключаемые возможности

Заранее ограничить размер проекта/CBOR, число узлов и экземпляров, объём
ресурсов/буферов Android, очереди обновлений и объём локальной истории.
Для провайдера отдельно задать пределы контекста, ответа, параллельных запросов,
числа шагов инструментов, попыток исправления и времени ожидания. Отмена
освобождает запросы и временные буферы; ответы старого задания не заменяют новый
проект. Фактические бюджеты выбираются после измерений на целевом телефоне.

Голос, внешние провайдеры, локальная модель, подключение МК и небольшой редактор
должны подключаться независимо. Самостоятельное открытие/просмотр JSON/CBOR
не требует работающей модели, микрофона, MCU или провайдерского сервиса.
История графиков принадлежит источнику данных и ограничена; пересоздание
телефонного UI не запускает неограниченное повторное накопление.

## Последовательность реализации

- [ ] Прототип Android: настоящий LVGL, общий C++ runtime и реальные общие
      JSON/CBOR-кодеки в выбранном host. Открыть один и тот же проект и проверить
      разметку, стили, биндинги, события и вложенные страницы. Измерить размер
      приложения, память и задержки; отдельно проверить фон/возврат/поворот.
- [ ] Подключаемые провайдеры и голос: сначала ввод текста и один кандидат
      endpoint, затем смена провайдера и распознавание речи. Проверить цикл
      ограниченного исправления по валидаторам и историю принятого проекта.
      Локальный/on-device вариант оценить отдельно без обязательства его включить.
- [ ] Связанный сценарий с МК: реальные каталоги, получение описаний по группам,
      проверка совместимости телефона/МК, preview, диагностика и отдельный save.
      Проверить конфликт revision, смену каталога и потерю сети без двойных команд.
- [ ] После основного голосового сценария: минимальные ручные правки и улучшение
      навигации по истории. Расширение редактора — по фактической необходимости.

Критерий первого законченного сценария: пользователь сформулировал запрос
голосом, исправил при необходимости текст, получил проверенный проект,
увидел его на LVGL телефона и смог отдельно показать на МК без неявного
сохранения. Подтверждение постоянной записи — следующий явный результат,
а не следствие удачного просмотра.

Этот план не добавляет зависимости, сервисные регистрации, сетевые запросы,
ключи провайдеров, Android-код или изменения прошивки. Перечисленные варианты
интеграции предстоит проверить в отдельных задачах.

## Windows как первый проверочный стенд

До Android-порта сценарии описаний и данных проверять на существующем настоящем
LVGL под Windows. Один JSON/CBOR-проект, общие кодеки/ядро и кодовый генератор
демоданных позволяют проверить биндинги, события, исчезновение/возврат данных,
вложенность, историю и групповой каталог без подключения платы. Это основной
дешёвый цикл проверки идеи. Android затем добавляет свой display/input adapter,
голос и выбранную оболочку; S3 отдельно проверяет аппаратную интеграцию и ресурсы.

07.11.2026 один созданный с нуля проект уже проверен на S3 через MCP и в Windows
как JSON и CBOR: показания `demo.speed` из кодового генератора, label binding и
переход между дочерними страницами. Это проверка существующего общего runtime,
а не реализация запланированных Android, моделей или нового каталога.

## Состояние 2026-11-08

Первая MAUI Blazor Hybrid версия Windows/Android реализована отдельно:
[руководство](../readme_maui_designer_ru.md). SPLA выполняет историю, модель и MCP;
небольшой интерфейс показывает чат, вложения и фактический кадр target.
Эта версия не реализует голос, локальный offline LVGL renderer на телефоне или
native HTTP MCP в прошивке. Эти пункты исходного плана остаются открытыми.
