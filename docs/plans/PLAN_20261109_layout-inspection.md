# Предложение: фактическая диагностика Grid/Flex

Статус: анализ. По последующему поручению владельца реализован только выбор
одна общая галочка «Тип вместо номера»: большие отдельные цифры либо G/F; см. readme_layout_debug.ru.md.
Сетка Grid и отдельный read-only инспектор остаются предложением.

## Наблюдаемый пример

Saved canvas/controls — обычный obj с LV_LAYOUT_GRID: две колонки 1fr/1fr,
три строки по 110 px, pad_column=70, pad_row=46, верх/низ=4. Шесть обычных кнопок
110×110 центрированы в ячейках. Общий стиль tile задаёт radius=20, border=1,
shadow_spread=3 и shadow_opa=185; на кнопках индивидуальные цвета и shadow_width=20.
Проверено через MCP: внутри controls — 6 button, 9 obj, 19 line, 1 label и 6
ui:polygon_button. Последние — лист/дом/колокольчик/язычок термостата и две
половины штор. Это общий native-компонент для произвольной фигуры, а не код
конкретного экрана. Внешние шесть плиток — стандартные LVGL button. Диагностические
outline и цифровые маски добавлены независимо от исходного оформления.

## Только стилями

Тип можно читать из lv_obj_get_style_layout(obj, LV_PART_MAIN) и выбирать фон-маску
G/F. Вариант меняет только внешний вид, не геометрию. Повторяемый тайл может содержать
букву; отдельной стилевой псевдонадписи в углу у LVGL нет. Точное угловое размещение
нельзя обещать без отдельной отрисовки/объекта или генерации изображения размеров контейнера.
Одно bg_image_src не складывает две картинки, поэтому G/F и цифру нужно объединять
в одном узоре либо выбирать режим. По последующему решению добавлены две отдельные маски G/F (64 байта),
без совмещения буквы с цифрой.

Нет стилевого свойства показа рассчитанных grid-линий. Регулярная bitmap-сетка —
декорация и не соответствует произвольным FR/CONTENT, span и пустым ячейкам.

## Read-only код при включённом debug

Снимать неизменяемый snapshot по запросу, в сериализованном UI-контексте после
обычной компоновки: layout, parent/child, coords/content coords, padding/border,
scroll, flags/state, flex flow/alignment/grow, grid descriptors/cell position/span.
Использовать публичные getters/has/read APIs; не менять свойства исследуемого UI,
не запускать отдельный таймер и не делать собственный layout engine. Snapshot можно
показывать в инспекторе рядом с кадром. Само отображение служебных меток требует
render/DOM, но исследуемое LVGL-дерево при таком пути остаётся неизменным.

В текущем LVGL 9.6 grid_update вычисляет x/y/w/h треков локально и освобождает их
через calc_free. Публичные getters дают описания треков и реальные прямоугольники
детей, не готовую таблицу итоговых треков. Рамки детей не равны ячейкам (на примере
кнопки центрированы). Для всех случаев FR/CONTENT/sub-grid/span точную сетку нельзя
восстановить только этими getters без повторения логики LVGL. Не опираться на
приватные поля/временные буферы и не дублировать grid calculator. Если точная сетка
понадобится, отдельно обсудить экспорт уже рассчитанных треков из LVGL; сейчас не делать.
