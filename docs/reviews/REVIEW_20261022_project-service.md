# Проверка проекта, ProjectService и редактора

> Результаты MCP в этом отчёте относятся к прежней реализации.
> Актуальные способы подключения описаны в [руководстве MCP](../readme_mcp_ru.md).


2026-10-22. Работа в `lvgl-cbor`; без коммита и публикации.

## Реализация

- Целые проекты JSON/CBOR: manifest, именованные экраны и общие стили. Общие PC-кодеки проверяют ссылки, зависимости и каталог устройства.
- `ProjectService`: const/файловая база + один RAM/файловый слой изменений, загрузка экрана по имени, отдельный preview, явная запись и контроль revision. Файловый адаптер использует два проверяемых поколения; монтирование и пути принадлежат приложению.
- Необязательный HTTP API и отдельный host MCP используют один ProjectClient. По умолчанию MCP разрешает чтение; предпросмотр и запись включаются независимо.
- Первая страница «Проект»: команды МК наверху, настройки рабочей копии и файл отдельно. Сервис сообщает права, базу/изменения и перечень носителей. База стенда находится в прошивке, изменения в RAM; FS/SD не настроены, наличие карты не проверяется.
- Стили: список слева, выбор/добавление/копирование/удаление, ПКМ; верхний selector убран. Используемый стиль удалять нельзя; переименование обновляет общие и экранные ссылки.
- Дерево компонентов: видимые иконки, ПКМ с каталогом компонентов и стилями, drag-and-drop до/после/внутрь контейнера, запрет переноса корня и циклов. Все изменения остаются черновиком до явного сохранения.

## Проверки

- 249 JS-тестов и 6 тестов MCP; нативная регрессия LVGL/TinyCBOR, включая ProjectService. `npm run contract:check` пройден; style ABI v2 и screen ABI v3 не менялись.
- Нативно проверены: заимствование ROM, overlay/reload/reset/удаления, фиксированная и read-only политика, конфликт revision, отказ записи без публикации, предыдущая файловая генерация после порчи новой, независимый preview и сохранение без переключения LCD. Файловые испытания выполнены на ПК; аппаратная SD не проверялась.
- В браузере: открытие с МК, явное сохранение с проверкой API, JSON/CBOR export/import; файлы компилируются в одинаковый CBOR. В экспортированном проекте сохранены нативный компонент, прикреплённый стиль и перенос message внутрь obj_1. JSON 3150 B, CBOR 1083 B.
- В браузере проверены список стилей, копирование/переименование/выбор, ПКМ добавления obj и прикрепления стиля. Реальный drag-and-drop изменил aria-level message с 2 на 3. Проверен Cream/Nano и Dark/Nano.
- S3: 8 аппаратных проверок, проект 9485 B. Preview не сохраняет; save не меняет дисплей; полный readback совпадает; stale revision и незавершённая/дублирующая передача отклоняются; экран загружается по имени. Проверена глубина 12 с нативным компонентом и составным массивом аргументов.
- На той же S3 после этого прошли 32 применения экранов и одно применение стиля через настоящий MCP stdio. Boot ID остаётся `s3-c24d6a7f`.
- Все 8 встроенных файлов побайтно совпали с устройством: исходный размер 518447 B, gzip во Flash 178059 B.

## Аппаратная установка

COMx, ESP32-S3 rev0.2, MAC `02:00:00:00:00:01`, Flash 16 MB, PSRAM 8 MB. Живая таблица разделов сверена с собранной; записан только app по `0x10000`, hash verified. BIN 1534624 B; SHA256 `f7b735ae830adc5f8ff47ad41c578be669f98a78a4df712b2b1c6d1e060f704a`. IP `192.0.2.1`. До входа в bootloader текущий RAM-проект считан; после прошивки восстановлен с исходной revision `62e44a9d57b6ae23`. Его сохранённый экран main оставлен на дисплее и сфотографирован USB-камерой; экспозиция камеры восстановлена.

## Стек и исправления

Ранние прогоны обнаружили panic HTTP-задачи. Уменьшены кадры обработчика: общий вход 928 → 352 B, transfer 1280 → 896 B. JSON INFO строится в отдельной noinline-функции до отправки: кадр info 1856 → 80 B. Проверка границ вложенного CBOR в ProjectService использует ограниченный стек курсоров вместо рекурсивных C++ кадров. Сохранение возвращает revision своего commit под mutex. При промежуточном сетевом прогоне был тайм-аут без перезагрузки; финальный прогон 8 проверок и следующий MCP-прогон завершились без отказов и смены boot ID. Измеренный минимум свободного стека HTTP-задачи после этих проверок: 472 B. Это результат конкретных прогонов, не гарантия произвольной нагрузки.
