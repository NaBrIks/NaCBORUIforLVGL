# Проверка MCP для биндингов, событий и вложенных страниц

> Результаты MCP в этом отчёте относятся к прежней реализации.
> Актуальные способы подключения описаны в [руководстве MCP](../readme_mcp_ru.md).


Дата: 2026-10-23. Исходный commit: `03f027e`. NTP и firmware-код этой задачей не изменялись; новой прошивки не выполнялось.

## Изменение

Общий `packages/project-codec/data-client.js` использует существующий `/api/data` и валидаторы screen-codec. Нет второго DataRegistry, обработчика прикладных действий или механизма навигации. Событие с instance поступает в существующий LVGL callback; настроенный navigate выполняет MCU runtime. MCP не добавляет специального прямого переключения контейнера.

Отличаются подтверждение очереди, результат исполнения и неподтверждённый исход. POST не повторяется; ошибка чтения результата не теряет ID принятой команды. Неизвестный/вытесненный результат не считается успехом. Схемы значений, writable и пути проверяются общими функциями; приложение остаётся окончательным владельцем проверки и выполнения.

## Реальный МК

Через настоящий stdio-процесс прочитаны capabilities, контракты, данные и проектный статус ESP32-S3 `192.0.2.1`. Получены 5 источников, композиция v1, root instance 9 и content pageInstance 10. Сохранённая revision `6c619acc862edd0e` не изменилась. Read-only запуск не регистрировал изменяющих runtime-инструментов. Артефакт: `local/mcp-runtime-hardware.json`.

Затем при разрешённой группе данных отправлен ровно один `send_event(node=nav-0,event=clicked,instance=9)` для уже выбранной страницы. Перед отправкой проверены совпадение показанной/сохранённой revision и отсутствие конкурентной смены display. Получен receipt id=1, state=completed, ok=true. Display и revision до/после совпали; bindingErrors/queueDropped/rejectedEvents=0. Артефакт: `local/mcp-runtime-event-hardware.json`.

Первый запуск аппаратного сценария завершился HTTP timeout до отправки события. Исходные 6 секунд в MCP были меньше допустимого server-side ожидания UI-команды; HTTP timeout MCP согласован с общим ProjectClient (15 секунд). Причина разовой сетевой задержки не установлена. Следующий запуск прошёл. Команды в неопределённом состоянии не повторялись. Проверка команд write_source/invoke_action выполнена на HTTP-стенде; реальные BLE-команды не вызывались, радио и проект не изменялись. Физическое касание этим не проверяется.

## Загрузка главного экрана и перезапуск веб-сервера

По дополнительному запросу владельца перезапущен только Vite проекта на `http://127.0.0.1:5298/`, HTTP 200 подтверждён.

Найдено: ScreenWorkspace при загрузке сохранял старый выбранный ID либо выбирал первый элемент списка. Поэтому manifest.entry=shell, записанный последним, не становился текущим экраном. Теперь начальный выбор и замена проекта предпочитают manifest.entry. Простое редактирование startup-поля не переключает текущий редактор. Отдельная регрессия проверяет стартовую страницу в конце списка и повторную загрузку при другом текущем экране.

Проверено в Chrome на изолированном origin `http://localhost:5298/`, без замены пользовательского черновика на canonical 127.0.0.1:5298. Открыт сохранённый MCU-проект: шесть страниц, entry shell; показана «Оболочка · время, сеть и страницы», статусбар, контейнер и пять нижних кнопок. Снимок: `local/mcp-entry-shell-ui.png`. На МК при открытии в редактор не сохранялось и не отправлялось preview.
