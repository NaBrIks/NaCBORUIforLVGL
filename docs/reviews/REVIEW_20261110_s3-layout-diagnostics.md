# S3: диагностика дерева и реальный кадр

## Результат

Программный тракт на 7-дюймовом ESP32-S3, LVGL 9.6 проверен. Физический LCD подтверждён владельцем после восстановления питанием на исходной рабочей прошивке; пробные аппаратные изменения отменены:
исходный проект с Setup и тремя прикладными страницами сохранён без изменения
ревизии. Получены настоящие RGB565 кадры 800×480. После проверки диагностика
выключена, параметры возвращены к 3 px / 75%; открыт Setup.
Windows Designer оставлен подключённым к S3 через Direct API. Каталог и выбранная
точка сохранились после перезапуска приложения. Ключ модели не извлекался в журнал.

## Реализация

Windows и S3 используют общий binder examples/common/layout_debug, одни
LayoutDebugOptions, runtime-стили и A1-маски. Отдельного рендера нет.
Уровни имеют независимые флаги и цвета рамки/метки. Общие настройки: толщина
1–16 px, прозрачность меток, номер либо G/F. Уровни отображаются по реальной
глубине дерева; на проверенном Setup доступны 0–4. Настройки временные, проект
не сохраняется. Для объектов без Grid/Flex режим G/F не создаёт букву layout.
Метаданные глубины публикуются до 4 Гц; команды выполняет DataApi через CBOR.

GET /api/view/frame обслуживает тот же NaWServer. Формат: BMP16 RGB565,
BITMAPINFOHEADER40, BI_BITFIELDS, маски F800/07E0/001F, top-down, DWORD stride.
Снимок 800×480 занимает 768066 байт PSRAM и выделяется только по запросу.
PNG на МК не кодируется. Один immutable snapshot арендуется ответом;
UI не перезаписывает арендованный буфер. Копирование выполняет LVGL task после
refresh, подготовка ограничена 1 Гц. Первый GET может вернуть 503 frame_warming_up,
параллельный — frame_busy, с Retry-After: 1. Клиент делает максимум два повтора.
frame_memory допускает новую попытку при следующем ручном запросе.
Удалённый ввод не рекламируется. MCP/JSON-authoring compiler на S3 не включён.

S3 использует синхронную конфигурацию TCP NaWServer. Поэтому кадр отправляется
штатным sendSource, удерживая RAII lease до возврата отправки. Во время отправки
большого кадра HTTP worker занят передачей; это не параллельный видеопоток.
Managed режим ради снимка не включался. PNG формируется в клиенте.

## Проверки

- JS suite: 372/372 PASS; BMP16 preflight и ограниченные warming/busy retry.
- Сборка S3: SUCCESS, static RAM 84956 Б, Flash 2070157 Б. Это размеры всей
  прошивки; ленивый snapshot в static RAM не входит.
- Перед записями подтверждены chip/MAC, реальная таблица разделов и CRC OTA.
  Записан только активный app OTA; хеш записи проверен. NVS, файловая система,
  bootloader, таблица разделов и OTA metadata не записывались. NTP не изменялся.
- Сохранённый проект до/после совпал целиком, включая ревизию.
- Через CBOR проверены выключенное состояние, рамки и метки, G/F и возврат OFF.
  Проверены BMP16 размер/заголовок и различие пикселей при смене диагностики.
- Из настоящего MAUI проверены рамка и метка уровня 3, G/F, толщина 5 px,
  прозрачность 128/255 и цвет рамки; значения сверены с источником на S3.
  В MAUI отображается настоящий кадр, контролы доступны. После проверки исходные
  диагностические параметры восстановлены; ошибок биндингов/очереди нет.
- После передачи кадров boot_id стабилен, повторная проверка uptime успешна.
  Аппаратные идентификаторы, сетевые адреса, baseline и кадры остаются в ignored local/.

## Исправления при аппаратной проверке

Первый запуск обнаружил отсутствующую группу ui перед установкой binder;
добавлена обязательная регистрация. После ручного BOOT восстановлена прошивка.
Вторая проверка выявила несовместимость sendOwnedSource с синхронной конфигурацией
TCP на S3; использован поддерживаемый sendSource без увеличения конфигурации сервера.
Промежуточные неудачные попытки не считались успешной приёмкой.

Также исправлена буквальная подпись SettingsNotice в настройках MAUI. Сборка
Windows без предупреждений и ошибок; исправление проверено после перезапуска.
Физическая LCD-приёмка без камеры не заявляется: проверен кадр реального framebuffer.

## Браузерная приёмка реальной S3

Headless Chromium открыл встроенный редактор в `/` самой платы. Получены два
BMP16 RGB565 кадра 800×480 / 768066 Б; проверены offset 66 и маски F800/07E0/001F.
Три ответа warming503 с Retry-After: 1 обработаны без ложной красной ошибки.
Изображение помещается в просмотр; возврат на «Макет» останавливает запросы кадров.
Пассивное переключение страниц авторинга и вкладок не изменило shell/setup на S3.
API-записей, команд render WebSocket и исключений браузера нет. Проект и ревизия
совпали до/после. Скриншот и измерения находятся только в ignored local/.

## Физический LCD: дополнительная проверка владельца

После программной приёмки владелец сообщил о циклических W/R/G/B заливках на
физическом экране при правильном framebuffer. Это опровергает вывод о полном
успехе вывода на LCD: кадр подтверждает память/рендер, а не саму матрицу.

По [официальной схеме Waveshare Rev1.2](https://files.waveshare.net/wiki/ESP32-S3-Touch-LCD-7/ESP32-S3-Touch-LCD-7-Sch.pdf)
LCD_RST подключён к EXIO3 CH422G. В прежней последовательности этот вывод всегда
оставался высоким. esp_lcd_panel_reset для RGB в ESP-IDF 5.5.6 сбрасывает FIFO и
LCD peripheral, но не внешний CH422G и не саму панель.

Добавлен аппаратный reset: 0x12 удерживает LCD_RST низким и подсветку выключенной,
не меняя TP_RST/SD_CS и оставляя USB_SEL низким. После запуска RGB clocks значение
0x1a отпускает reset, затем штатное 0x1e включает подсветку. Пины, PCLK и тайминги
RGB не менялись. Собрано и записано только app OTA после проверки MAC/OTA и хеша.
Проект сохранился, Setup открыт, bindingErrors=0.

Причина заливок как latched test state пока гипотеза. После этой прошивки запрошена
физическая проверка владельцем; до ответа дефект LCD не считается закрытым.


### Уточнение после ответа владельца

Аппаратный EXIO3 reset не устранил циклические заливки. Проверка после отдельного
перезапуска без намеренных запросов framebuffer также дала W/R/G/B. Владелец
подтвердил, что раньше эта матрица показывала TPMS/Radar/Trip и Setup, а проблема
возникла около этапа обсуждения MCP. Это регрессия, не принятая аппаратная работа.

Временная диагностическая сборка прочитала реальные GPIO: все 20 RGB outputs
включены, mux=1, signal indices совпадают с LCD_DATA0..15, DE, HSYNC, VSYNC, PCLK.
Выключение подсветки через временную diagnostic.lcd_backlight подтверждено
владельцем на физической матрице; после проверки подсветка восстановлена.
Смена регистрационного binder/MCP не перенастраивает эти GPIO.

Для контролируемого сравнения возвращается прежняя UART-console sdkconfig;
неудавшийся пробный аппаратный reset убран, исходная последовательность дисплея
восстановлена. Временная GPIO/подсветочная диагностика подлежит удалению после
локализации. Частоты, RGB timing и питание EXIO6 наугад не менялись.

## Контроль готовой демкой без компиляции

По отдельному поручению владельца использован уже собранный touch_lcd7 app от
20 октября (ESP32-S3, ESP-IDF 5.4.0), без каких-либо изменений или сборки.
SHA-256 исходного файла и локальной копии совпал. После проверки MAC/OTA записан
только активный app; хеш записи проверен. Перед этим сохранены локальные сырые
копии проектного SPIFFS и NVS; таблица разделов/bootloader не записывались.
HTTP подтвердил запуск другого приложения: корень отвечает HTML, прежний /api/info
отсутствует. Это отдельная демка для проверки LCD, не прошивка Designer/MCP.
Визуальная оценка владельца запрошена; результат пока не предполагается.

## Решающий контроль питания

Владелец подтвердил: готовая touch_lcd7-демка сначала также показывала только
W/R/G/B. После извлечения кабеля и ожидания появились ожидаемые полосы и надписи.
Таким образом, для контрольной демки требовалось полное снятие питания; обычные
ESP reset/перепрошивка и пробный EXIO3 reset этого состояния не устранили.
Сам по себе этот результат ещё не подтверждает холодный запуск нашей прошивки.

Без компиляции возвращён ранее проверенный полный app нашей версии с биндингами,
Setup и RGB565 preview. Хеш записи проверен, сохранённый проект совпал полностью,
bindingErrors=0. Никакой FS/NVS restore не потребовался. Временные GPIO и
backlight diagnosis удалены из исходников; не подтвердившиеся аппаратные правки
и переключение консоли для эксперимента отменены. Владелец выполняет холодный
старт уже нашей версии; его физическое подтверждение ожидается.

## Итоговая физическая приёмка

Владелец подтвердил: после повторного отключения питания и включения без BOOT
на нашей ранее собранной прошивке появился интерфейс с нижним меню.
Программная проверка после подтверждения: исходный проект и ревизия сохранены,
bindingErrors=0, Setup открыт; MAUI кадр обновлён. Повторной компиляции не было.

Во время этого успешного физического восстановления boot_id МК и его uptime
продолжили прежний сеанс. Поэтому не заявляется холодный перезапуск самого ESP32:
подтверждено восстановление именно физического LCD после действий с питанием.
Точная внутренняя причина режима W/R/G/B не установлена; эксперимент показал, что
он сохранялся при MCU reset и разных app-бинарниках и исчез после действий с
питанием панели. Связывать его с MCP или исправлять частотами оснований не найдено.

Временные диагностические команды, GPIO dump и пробные аппаратные правки удалены
из исходников; возвращён проверенный рабочий app без них. Полный физический дефект
для текущего сеанса закрыт подтверждением владельца, а не только framebuffer.
