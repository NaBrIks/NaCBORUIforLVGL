# NaWServer: обновление интеграции, S3 и Windows

> Результаты MCP в этом отчёте относятся к прежней реализации.
> Актуальные способы подключения описаны в [руководстве MCP](../readme_mcp.ru.md).


Дата: 2026-11-07. Проверены полный пример для Waveshare ESP32-S3-Touch-LCD-7
Rev1.2, ESP-IDF 5.5.6, LVGL 9.6.0 и соседний NaWServer `318732c`.
Код соседней библиотеки не менялся. Адреса, USB-идентификаторы и исходные журналы
аппаратной проверки остаются в ignored local/.

## Изменения сборки

Первая сборка выявила удаление `HandlerBase::canHandle` в новом NaWServer.
DataApi, ProjectApi и embedded assets переведены на `routes() const` с точными
стабильными `RouteDescriptor`. Сохранены существующие URL и обработка методов,
включая OPTIONS/405. HTTP/WS и владение запросами остаются в NaWServer;
прикладные очереди и выполнение LVGL — в существующей UI-задаче.

Удалены прежние backend selector-настройки TCP/HTTPD. `build_s3.ps1` очищает их
из существующего sdkconfig, сохраняя WebSocket и размер HTTP stack. Числа ABI,
кодеки и движок биндингов не менялись. Изменение dependencies.lock затрагивает
только manifest hash; версии управляемых зависимостей не изменены.

При проверке упаковки обнаружено, что browser production build содержал notices,
а firmware packer забирал только index/assets. Теперь включает и `licenses/*.txt`
с MIME text/plain. На плате сверены все **13 файлов**: 643695 байт исходных
assets, 217021 байт gzip во Flash, включая notices Vue/cborg/Tabler.

Финальная S3-сборка — PASS. Linker сообщает 84796 байт статической RAM и
1985105 байт Flash; это не оценка полной runtime RAM. Размер app image:
1985504 байт, SHA256 `438849e2802548f5b77a65f8213184237a754849a4a01de3a6366b5cbab501cf`.

## Развёртывание и аппаратные проверки

Целевая плата опознана по USB serial и подтверждена esptool: ESP32-S3,
8 MiB PSRAM, 16 MiB Flash. Текущая таблица оказалась OTA, а не factory-разметкой
старого примера. Из прочитанной таблицы и boot log подтверждён активный ota1.
Записано только приложение в этот существующий слот; esptool проверил hash.
Bootloader, partition table, NVS/PHY, OTA selection и общий project SPIFFS
не записывались. Успешно смонтирован существующий раздел, сохранённый проект
доступен. Обычный factory-only deploy helper не запускался в обход его проверки.

На окончательном образе:

- 20 циклов параллельного INFO/capabilities/data, один boot_id, без новых binding
  errors; style, screen и component WS получили валидные CBOR acknowledgements.
- Все 13 HTTP-assets совпали с локальным production build байт в байт после
  распаковки; исходные URL API сохранены.
- Существующая composition-проверка: локальная навигация, retain/cache reuse,
  release/recreate, ошибка циклической загрузки и возврат к полноценному preview.
  Эти сценарии также проверены перед финальным добавлением license-assets.
- Настоящий MCP stdio client получил каталог платы. Из пустых документов создан
  проект с тремя страницами и live binding на demo.speed.kmh; общий codec собрал
  1881 байт CBOR. Preview и диагностический clicked переключили дочернюю страницу.
  Ревизия сохранённого проекта не изменилась; сохранённый entry восстановлен.
- Автономный генератор: за 4.2 s получены 24 coalesced data_changed кадра скорости,
  последовательность отсчётов растёт, значения дробные/плавные. После закрытия
  WS источник продолжил публиковаться. Источники clock/network также читаются.
- Считаны именно наблюдения framebuffer из style ACK: два заданных RGB565-цвета
  центра, красная граница и рост frame_count. После проверки возвращён entry.
- В финальном измерении: свободно 76911 байт internal heap, 4728088 байт PSRAM,
  HTTP task stack_free 5516 байт. Binding errors, queueDropped и rejectedEvents — 0.
  Повторное чтение подтвердило рост uptime при неизменном boot_id.

Камеры и владельца у панели нет: физическое качество изображения, подсветка и
ручной touch не проверены. Framebuffer/драйверные и программные проверки не
обозначают визуальную приёмку физической панели.

## Windows как основной стенд описаний

В существующем настоящем Windows LVGL проверены тот же созданный с нуля проект
как JSON и CBOR, кодовый генератор через publish_cbor, фактически отрисованный
текст биндинга и событие вложенной навигации. Скрытые окна не использовали мышь
или клавиатуру; их снимок просмотрен.

Полная Windows-регрессия 12 стандартных типов, четыре схемы, writeback, popup,
ошибочные загрузки и JSON/CBOR — PASS. Resize всех четырёх страниц на пяти
размерах — PASS. Системная проверка: 32 logical CPU, RAM, три GPU-записи, история
32 отсчёта вне страницы, missing/rejected values и стабильная геометрия — PASS.

Обнаружена неточность прежнего system test: при третьем GPU он требовал,
чтобы даже невидимое содержимое явно прокручиваемого списка помещалось в page
viewport. Исправлен только тест: проверяет непосредственного родителя и владельца
прокрутки. У корня страницы overflow нет. Строгая проверка обязательного GPU
counter отдельно встретила недоступный счётчик; не заявляется, что все три
адаптера предоставляют валидную загрузку. Поддержка unknown не превращена в ноль.

JS 311/311, MCP 8/8, contract:check, production build и Uncrustify Check 93 C/C++
файлов — PASS. Native runtime в этой задаче не переписывался; Windows EXE
переиспользована для проверок общего движка, новой Windows-сборки не заявляется.
