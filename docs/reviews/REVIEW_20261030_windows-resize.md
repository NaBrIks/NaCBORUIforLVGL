# Windows: изменение размера окна и адаптивные страницы

Дата: 2026-10-30. Задача владельца: графики и страницы должны использовать
доступное место при изменении размера Windows-окна.

## Изменения

- LVGL Win32 backend включён в обычном desktop-режиме (`simulator_mode=false`):
  рамка изменения размера и разворачивание доступны. WM_SIZE и framebuffer
  обслуживает исходный backend LVGL 9.6.0, без копирования его реализации.
- Нативное меню учитывается при расчёте client area. Стартовый размер области
  действительно равен проектному, а не уменьшается на высоту меню.
- `ScreenViewport::Display` — явный параметр C++ хоста. Он позволяет открыть
  проект в уже изменённом дисплее. По умолчанию остаётся Declared; несовпадение
  размеров при загрузке в этом режиме по-прежнему отвергается.
- Shell, Обзор, Данные, Настройки и Система используют обычные Grid/Flex-команды,
  процентные размеры и FR из существующего JSON/CBOR-контракта. Статусбар 28 px,
  нижнее меню 44 px; между ними — всё оставшееся место.
- Большие и малые графики растут с доступной площадью. Их история и указатели
  объектов не зависят от изменения геометрии. Для более 32 логических процессоров
  и двух GPU остаётся собственная область прокрутки; при достаточной высоте
  её содержимое тоже растёт и занимает доступную площадь.
- Настройки сохраняют плотное расположение обычных контролов; растёт поле ввода,
  контейнеры и ширина колонок. Круглый мини-пример дуги сохраняет квадрат 100×100,
  чтобы родной LVGL arc и его значение не расходились в прямоугольной ячейке.

Нормальная демка имеет минимальную client area 800×480. Небольшие самостоятельные
проекты могут стартовать со своим меньшим минимумом. Максимальный размер окна
ограничен 4096 px по каждой стороне; первичная проверка размера файла/документа
остаётся прежней. Шрифты не растягиваются, раскладка не угадывается по ID.
Автоматическая адаптация топологии относится только к встроенной демке.

## Приёмка

- Release-сборка — PASS. Настоящий Win32 client resize проверен через CBOR-команду
  `resize` → SetWindowPos, затем штатный WM_SIZE/backend/LVGL.
- Последовательность 800×480 → 1200×800 → 1600×900 → 1024×768 → 800×480.
  На каждом размере проверены все четыре страницы и их компоненты.
- Корни страниц в точности совпадают с контейнером между статусбаром и меню.
  Кнопки меню без зазоров занимают всю нижнюю ширину; ни один видимый компонент
  не выходит за свой контейнер. В конфигурации 32 CPU / 2 GPU скролл не требуется.
- Меняется размер текущего экземпляра; ID экземпляра при resize постоянен.
  `demo.level=67` и `demo.text=Resize` сохраняются при проходах по страницам и
  размерам; последовательность системного источника продолжает увеличиваться.
- Проект CBOR с проектным размером 800×480 успешно загружен в дисплей 1200×800.
  Размер окна не сброшен; неверный resize 200×100 отвергнут без смены страницы
  и геометрии.
- Прежние Windows-проверки всех 12 типов, четырёх схем, popup, writeback,
  фокуса/EDITED, JSON/CBOR и ошибочных загрузок — PASS.
- Настоящие CPU/RAM/GPU, полная история 32 отсчёта и сбор вне страницы — PASS.
- Native suite — PASS, включая отдельную проверку Declared/Display: строгий
  режим отвергает другой размер, адаптивный загружается, следует изменению
  display без замены корня и допускает повторную загрузку.
- Общие JS-тесты **310/310**, `contract:check` — PASS; wire ABI без изменений.
- Production-сборка браузерного редактора — PASS. Модель SeMaps обновлена
  через MCP и сохранена, `semaps check` без замечаний; геометрия не менялась.
- Новая Release EXE установлена и запущена; хеш установки совпадает со сборкой.
  У настоящего видимого окна подтверждены WS_THICKFRAME и WS_MAXIMIZEBOX,
  оно не перехватило foreground. Существующая выбранная схема сохранена.

Просмотрены LVGL-снимки на разных размерах. Приёмка дополнительно обнаружила
недостаточную высоту строки изображения/подписи в Настройках — исправлено;
проверены именно компоненты, а не только отсутствие полос прокрутки.
Высота текстовых узлов дополнительно сверена с line height фактического шрифта;
увеличена строка заголовка Настроек, которой не хватало нескольких пикселей.
Данные остаются в истории, заново не генерируются для размера графика.

Команды: `npm run player:build`, `npm run player:test`,
`npm run player:test-system`, `npm run player:test-resize`,
`powershell -NoProfile -File tools/test_native.ps1`, `npm test`.
Снимки и измерения — ignored `local/windows-resize`, локальные журналы не
публикуются. Проверки выполнялись в скрытых окнах, без OS-ввода и активации.
Платы, NTP и сеть не использовались. Геометрия SeMaps не менялась.

Нативные снимки настроек: [800×480](../images/windows-responsive-800.png) и
[1600×900](../images/windows-responsive-1600.png). Значения полей на них —
проверочные данные; это снимки LVGL, не рабочего стола.

## Группировка системного обзора Flex

Следующее уточнение владельца выполнено обычными Flex-командами JSON/CBOR.
Получились четыре блока с тонкими границами текущей схемы: CPU целиком и по
логическим процессорам, RAM, загрузка GPU, память GPU. CPU занимает верхнюю
область; RAM/GPU/GPU memory делят нижний ряд поровну. Внутри CPU строки графиков
также построены Flex. Графики заполняют доступную область, строки памяти GPU
сохраняют компактную высоту. Новых источников, C++-обработчиков и методов нет.

Повторная приёмка: 310 JS-тестов, Windows regression, реальные CPU/RAM/два GPU
с 32 отсчётами и четырьмя схемами — PASS. Resize всех страниц 800×480, 1200×800,
1600×900, 1024×768 и обратно — PASS. Дополнительно проверены четыре отдельные
границы блоков, равная ширина нижних блоков, отсутствие перекрытий и выходов
за родителя. Просмотрены реальные LVGL-снимки на малом и большом окне.
