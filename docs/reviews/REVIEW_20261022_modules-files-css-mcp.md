# Модульный редактор, файлы, CSS, MCP — 2026-10-22

## Результат

Реализованы независимые document-io и css-codec, подключаемые Vue-модули файлов и CSS, отдельный MCP-адаптер на ПК и вариант s3-no-editor. Нативный ABI v3/v2 и регистрация компонентов не менялись. Полная версия редактора записана на ESP32-S3 COMx, MAC 02:00:00:00:00:01. Прочитана и сверена таблица разделов, записано только приложение 0x10000; esptool подтвердил hash. Таблица разделов, bootloader и NVS не перезаписывались.

Редактор доступен локально на http://127.0.0.1:5298/ и с платы на http://192.0.2.1/. Код и конфигурация MCP-клиента автоматически не подключались к Codex; сервер проверен как отдельный stdio-процесс настоящим MCP-клиентом.

Записанный firmware.bin: 1 465 792 байт; SHA-256 78551562a0b64ac396e2ac2b6b2cacc7fd6c852cbfe59037e6b2828db85e87c0.

## Размеры

Одинаковые toolchain, LVGL 9.6.0 и sdkconfig (различий строк полных sdkconfig нет). Полная сборка и s3-no-editor используют одни исходники, отличается флаг LVGL_CBOR_EMBED_EDITOR.

| Показатель, байт | Полная сборка | Без встроенного сайта |
|---|---:|---:|
| Flash, отчёт PlatformIO | 1 465 392 | 1 308 620 |
| Статическая RAM | 140 584 | 140 504 |
| Сжатые web-файлы | 155 901 | 0 |

Исключение сайта экономит 156 772 байта Flash и 80 байт статической RAM. Разница Flash включает массивы, метаданные и обработчик HTTP. По ELF в s3-no-editor нет символов asset_N и asset_handler. Этот вариант собран и проверен по ELF, на физическую плату не записывался.

8 встроенных файлов до сжатия занимают 444 026 байт. Они хранятся во Flash gzip-массивами; распаковываются браузером, а не S3. Это размер файлов, не измерение JS heap браузера. HTTP/WS имеют свои рабочие буферы. Большие dist/reference в прошивку не включены.

check_optional_modules.mjs проверяет отсутствие JS- и CSS-chunks отключённых модулей. Общая оболочка и базовые кодеки остаются. MCP отсутствует в этих сборках полностью, SDK установлен только в integrations/mcp.

## Автоматические и браузерные проверки

- 225 JS-тестов: прежняя регрессия плюс JSON/CBOR roundtrip всех примеров, порча/обрезка пакетов по каждому смещению, ограничения, неверные форматы/UTF-8, CSS-значения/состояния/части, каскад/important/специфичность, атомарные отказы, обратный экспорт и 300 детерминированных некорректных строк.
- Три нативных исполняемых теста с реальными LVGL 9.6/TinyCBOR и проверка native registration → actual capabilities → PC compiler пройдены.
- contract:check пройден: style v2 SHA efdbe8aee4e961473bf8d671142361b1feb5ee8c582801d005acf1cd739acef2, screen v3 SHA fad10d7e4c7c808a22b5ce06af537f4c0062d458e5dc1ad8d4dff15cd788f050.
- Пять MCP-тестов: настоящий stdio initialize/list/call; compile/decode/CSS; инструменты записи и CSS полностью отсутствуют при отключении; MCP_ENABLED=0 завершается без инициализации; проверены чужие ACK, неверные возможности/ABI, закрытие WS, таймаут, очистка busy и запрет параллельной команды.
- В браузере на 5298: сохранение/загрузка JSON и CBOR как экрана, так и стиля; CSS из поля и файла, экспорт/копирование, блокировка неподдерживаемого свойства, успешный ACK после применения. Скриншот просмотрен: действия компактны, общий обзор сохранён, CSS-панель свернута по умолчанию.
- В браузере непосредственно с S3: модули загружены с платы, JSON импортирован, CSS применён, реальный экран принят. Повреждённый CBOR дал ошибку, название/документ сохранились; затем корректный JSON снова загружен.

## Аппаратная проверка

Через официальный MCP-клиент/stdio и реальные HTTP/WS платы прошли 1 запись стиля и 32 замены экранов: по два файловых формата для шести примеров плюс 20 повторов CSS export/import → JSON/CBOR → применение. До/после один boot_id, перезагрузок в ходе теста не было. Это проверка корректности и повторной загрузки, не бенчмарк скорости или динамического heap.

check_embedded_assets.mjs побайтно сверил каждый встроенный web-файл с dist; все совпали. На USB-камере виден реальный LCD с заголовком JSON / CBOR / CSS / MCP и шкалой 75%. Камера подтверждает раскладку/надписи и видимость объектов; точная цветометрия и сравнение пикселей не выполнялись.

Один HTTP-запрос сразу после аппаратного сброса превысил 5-секундный таймаут. После появления API повторная побайтная проверка и полный аппаратный прогон прошли. В финальном прогоне boot_id до/после: s3-5220e2db.
