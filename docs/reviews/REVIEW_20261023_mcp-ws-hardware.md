# ESP32-S3: MCP → WS → браузер, конфликт и возврат на главный экран

> Результаты MCP в этом отчёте относятся к прежней реализации.
> Актуальные способы подключения описаны в [руководстве MCP](../readme_mcp.ru.md).


Дата: 2026-10-23. Это приёмка на настоящем устройстве, дополняющая [первоначальную проверку](REVIEW_20261023_project-live-sync.md).

## Устройство и окончательная прошивка

- Waveshare ESP32-S3-Touch-LCD-7 Rev1.2, COMx, MAC `02:00:00:00:00:01`. Chip/MAC проверены esptool перед записью.
- Обновлено только приложение с `0x10000`; таблица разделов проверена на совпадение. SPIFFS, NVS, PHY и bootloader не записывались.
- Окончательный firmware.bin: **2 206 416 байт**, SHA-256 `2c6a0137a2148127cb74283b16f42d186865977e63de326a734b09ab2198374b`. Esptool подтвердил hash записанных данных.
- После загрузки: IP `192.0.2.1`, `boot_id: s3-8ddf5d3b`, LVGL 9.6.0. Возможности объявляют `project.events:["project_changed"]`.
- До прошивки проект прочитан через настоящий stdio MCP в `local/ws-hardware-project-backup.json`. Ревизия `ba3c561d966c4815` сохранилась после app-only обновления.
- Все восемь файлов встроенного сайта побайтно совпали с `frontend/dist`: 600 764 исходных байта, 200 733 байта gzip. Результат — `local/modules-device-assets.json`; данные прошивки — `local/s3-deployment.json`.

Финальная проверка ниже выполнена во встроенном редакторе **http://192.0.2.1/** в Chrome; предварительно тот же сценарий проверен из локального редактора. Вкладка владельца на `127.0.0.1:5298` не использовалась. Изменения сохранённого проекта выполнялись только MCP-инструментом `save_project`; браузер читал результат существующим API и принимал события существующего `/ws`.

## Подхват без перезагрузки

1. Явно открыли проект с МК, выбрали dashboard и оставили эту страницу редактора открытой.
2. Через MCP изменили заголовок на `WS / MCP LIVE` и проектную высоту с 408 до 400, сохранили с исходной ревизией.
3. МК вернул ревизию **`a452c0c6585e63d9`** и отправил бинарное CBOR-событие `{v:1,event:"project_changed",revision:"a452c0c6585e63d9"}`. Независимый WS-наблюдатель получил ту же ревизию. Ответ MCP зафиксирован в 09:45:32.264Z, событие — 09:45:32.291Z; это время приёма наблюдателем, не измерение отрисовки браузера.
4. Уже открытый dashboard сам показал новый заголовок и **800×400**. Повторного открытия проекта, перехода на другую страницу или перезагрузки браузера не было. Выбор dashboard сохранился.

Протокол: `local/ws-hardware-change.json`. Снимок: `local/ws-hardware-browser-live.png`.

## Конфликт с локальной правкой

1. В браузере введено локальное название проекта **«Локальная правка · проверка МК»**.
2. Через MCP сохранено следующее внешнее изменение dashboard: заголовок `WS / MCP CONFLICT`, высота 398. Ревизия МК — **`1abf959fedbfcce3`**; WS передал её же.
3. Браузер показал предупреждение о конфликте. Локальное название сохранилось; локальная версия dashboard осталась `WS / MCP LIVE`, 800×400. Внешний документ её не заменил.
4. Отдельная попытка MCP-сохранения со старой ревизией `a452c0c6585e63d9` получила **HTTP 409 `project_revision_conflict`**. Повторное чтение подтвердило, что сохранённая ревизия не изменилась.

Протоколы: `local/ws-hardware-conflict.json`, `local/ws-hardware-stale.json`. Снимок: `local/ws-hardware-browser-conflict.png`.

## Восстановление проекта и иконка домика

Через MCP восстановлен исходный dashboard. Весь сохранённый проект после теста совпал с резервной копией, включая исходную ревизию **`ba3c561d966c4815`**. Тестовую локальную правку удалили явным открытием восстановленного проекта. Для успешных save/read-проверок сравнивали состояние композиции до/после: сохранение не переключало LCD.

Для проверки возврата через MCP показан несохранённый вариант оболочки с начальной страницей radar. Прямой корневой preview дочерней страницы 800×408 не соответствует физическому дисплею 800×480 (`display_size_mismatch`), поэтому дочерний экран проверялся внутри оболочки. Сохранённый проект при preview не изменялся.

Во встроенном сайте, оставаясь в редакторе другой страницы, нажали выделенную SVG-иконку домика в верхней строке. Кнопка прочитала сохранённый entry МК и показала **shell**, `preview:false`, с выбранным **dashboard**. Она не переключила страницу браузера и не заменила его локальный документ. Дополнительно проверено отличие локального entry «Экран 1» от сохранённого entry shell: использован именно сохранённый entry. В подсказке кнопки получен результат «Показан сохранённый экран shell».

Снимок: `local/ws-hardware-home-button.png`. Протоколы: `local/ws-hardware-preview.json`, `local/ws-hardware-restore.json`, `local/ws-hardware-final.json`. Финальная композиция: root instance 8, child instance 9, shell/dashboard, без ошибки загрузки.

## Диагностика и проверки сборки

- На этапах change/conflict/restore/final `boot_id` оставался `s3-8ddf5d3b`; перезапусков в ходе финального сценария не было.
- `bindingErrors: 0`, `lastError` пуст. BLE продолжал сканировать: пакеты 1340 → 1474 → 1611 → 1759, массив содержит 16 устройств, dropped 0. Команды остановки/очистки радио не выполнялись.
- `npm test`: **293/293**; MCP stdio/API: **8/8**; `npm run contract:check`: успешно. Production-сборка редактора: 176 модулей; сборка S3: успешно.
- NTP-код, список серверов, часовой пояс, sdkconfig и firewall не менялись. Только по дополнительному вопросу владельца прочитано состояние источника: `syncState:"syncing"`, подтверждённое время пока отсутствовало. Существующая конфигурация содержит три сервера: `ntp1.yandex.ru`, `pool.ntp.org`, `time.google.com`.

Снимки и подробные JSON-протоколы находятся в игнорируемом `local/`; они не включены в исходный коммит. Эта проверка подтверждает протокол, браузерный интерфейс и состояние ProjectService. Снимок физического LCD камерой в данной приёмке не выполнялся.
