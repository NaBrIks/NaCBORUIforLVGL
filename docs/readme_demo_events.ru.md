# Демопроект: размеры страниц и живые CBOR-данные

Обновление 2026-10-28. S3-пример имеет экран 800×480, статусбар 28 px и нижнее
меню 44 px. Область вложенных страниц — **800×408**. Общие числа определены
в `examples/s3_style_lab/project/shell.mjs`; dashboard/radar/trip используют
`contentSize` и явную компоновку всех компонентов под эту область.
Нативные компоненты также имеют конечные размеры, включая внутренние подписи.
Это адаптация поставляемой демки, не автоматическое масштабирование произвольных
проектов и не отключение прокрутки для сокрытия переполнения.

`tools/project_image.mjs` генерирует ROM-базу и проектный SPIFFS с этими размерами.
После сборки приложения и SPIFFS явный `deploy_s3.ps1 -UpdateFilesystem` записывает
оба образа; обычное обновление приложения сохраняет прежний слой изменений.
Чтобы существующий проект получил новый layout, необходимо явно обновить его
сохранённый слой. Входной Project JSON по-прежнему сохраняет авторские правки.

## Генератор и биндинги

Прикладной `main/demo_speed.cpp` независимо от экранов и веб-клиентов создаёт
скорость 0–180 км/ч по непрерывной косинусной траектории с периодом 24 секунды.
`esp_timer` публикует отсчёты 25 Гц. Значение определяется абсолютным прошедшим
временем: задержка не создаёт очередь догоняющих измерений.

Паттерн основного приложения учтён архитектурно: отдельный ESP event loop,
копируемый CBOR payload и рассылка нескольким потребителям. Код основного
приложения не копировался и зависимость от него не добавлялась.

```text
автономный таймер → CBOR → bounded ESP event queue (4 кадра × до 192 Б)
  → UI dispatcher → DataRegistry.publish_cbor("demo.speed") → flush
    → биндинг экземпляра страницы → reading_number → отрисовка стрелки
    → общий адаптер data_events → CBOR /ws → runtime-снимок браузера
```

Источник `demo.speed` — readonly-структура `{kmh:number,unit:text,sequence:integer}`.
Стрелка сохраняет дробную позицию. Метод `reading_number` добавлен с локальным
opcode 260; прежний целочисленный `reading` 258 и остальные номера сохранены.
Генератор не знает объектов LVGL, их ID, страниц или соединений.

Источник продолжает публиковать вне страницы. При возврате активируется биндинг
и берёт последний committed-снимок, не начинает генерацию заново.

## Браузер

Общий адаптер `main/data_events.*` наблюдает явно выбранные приложением источники
и после `flush` отправляет последние снимки через существующий `/ws`:

```text
{v:1,event:"data_changed",source:"demo.speed",state:"known",
 revision:123,value:{kmh:42.125,unit:"km/h",sequence:100}}
```

Это CBOR map, не JSON-строка. Состояния `unknown` и `stale` передаются явно.
Снимки объединяются, частота ограничена десятью отправками в секунду на источник;
кадр ограничен 3584 Б. При backpressure повторяется последнее состояние.
Clock/network передаются тем же механизмом, без отдельного протокола.

Редактор делает один bootstrap GET `/api/data` при подключении/переподключении,
затем использует события. Runtime-снимки отделены от авторского проекта:
не сохраняют показания в проект, не включают dirty и не вызывают автоприменение.
Защищены запоздалый HTTP-ответ, reset/reconnect и более новые события.
Разбор выражений и форматирование берутся из общих кодеков.

CSS-предпросмотр обновляет поддерживаемое текстовое/числовое содержимое;
для нативного компонента показывает текущие аргументы его биндинга в общем
placeholder. Его графика исполняется настоящим LVGL на МК; отдельный renderer
спидометра в универсальный редактор не добавлен. Общие state/style-команды
LVGL в браузере пока не эмулируются.
