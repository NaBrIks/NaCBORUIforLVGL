# Архитектурное направление первого этапа

Здесь сохранены проектные решения и эскизы октября 2026. Текущее поведение
описано в руководствах по [проектам и API](readme_projects_ru.md),
[биндингам](readme_bindings_ru.md), [вложенным страницам](readme_page_composition_ru.md)
и [исполнителю](readme_fast_executor_ru.md).

Уточнение владельца 2026-10-21: для именованных стилей принять минимальное разделение на глобальные стили и стили конкретного экрана. Их хранение и замена определяются нашим проектом, а не диктуются LVGL. Не вводить без необходимости сборщик неиспользуемых стилей, дополнительные классы владения и произвольные цепочки зависимостей. Первая реализация закрепляет полную замену записи со стабильным адресом; освобождение областей при переключении экранов ещё предстоит реализовать. Стили экрана в этом смысле не тождественны локальным свойствам одного объекта (`lv_obj_set_style_*`) в API LVGL.

Уточнение нумерации таблиц 2026-10-21: каждое семейство API обрабатывается отдельно и имеет собственную нумерацию сигнатур с нуля. После сравнения вариантов в первом опыте выбрана **одна таблица shared**: младший байт — сквозной индекс метода в этом семействе, старший — проверяемая сигнатура. Нумерация закреплена в [JSON-контракте v1](../contracts/style-api-v1.json) отдельно от сортировки HTML. Вариант отдельных таблиц на сигнатуру сохранён для сравнения в протоколе.

[Исходный вариант](ideas/IDEA_20261020_lvgl-cbor_event-message-bindings.md) уточнён [принятым ADR данных/событий](adr/ADR_20261022_data-bindings-events.md): загрузчик дерева независим от адаптеров сообщений, а приложение регистрирует типизированные символические источники и действия. Реестр принимает принадлежащие ему значения или ограниченно декодируемый CBOR. Адаптеры BLE/TPMS/GPS находятся вне ядра. Отдельный Subject на каждое поле не нужен.

[Развитие модели](readme_bindings_ru.md): обработчик событий извлекает востребованные значения в именованный реестр, а привязки определяют зависимости и обновления свойств. Спрос складывается из постоянных подписок и подписок экранов; одно значение может обслуживать несколько элементов. Постоянные подписки работают при переключении экранов. При включении неизвестное значение отображается как `--`; при возврате используется последнее известное значение, если оно продолжало обновляться или доступно у приложения. Скрытие и уничтожение экрана различаются.

```text
JSON (редактируемый исходник)
  -> преобразование на компьютере
CBOR (символьные имена, типизированные значения)
  -> декодер на устройстве
Исполнитель описания
  -> объекты, стили и биндинги LVGL
```

Доставка документа и загрузка ресурсов должны иметь явные границы с исполнителем. Для первого опыта стилей выбран binary CBOR по WS; файловая загрузка и доставка целых экранов ещё не реализованы. Новая композиция экрана использует виджеты, источники данных и действия, уже доступные в прошивке.

Необходимо описать жизненный цикл входного буфера, строк, шаблонов, объектов LVGL и подписок. Возможность освобождать входной CBOR после создания экрана — предмет проектирования, не готовая гарантия.

Сравнение с XML должно разделять парсер, исполнитель, сохраняемые описания и память самого LVGL. Для точных цифр потребуется одинаковый экран, одинаковый набор возможностей, фиксированные версии и параметры сборки, сравнение map-файлов и пикового heap.

## Составление именованных стилей: copy и merge

Указание владельца 2026-10-21: органично включить `lv_style_copy` и `lv_style_merge` в минимальную модель глобальных и экранных стилей. Это операции составления самостоятельного стиля; дополнительных областей владения они не вводят.

Ранний эскиз композиции ниже не является точным JSON v1. Реализованный документ содержит поля `scope`, `name`, `copy`, `merge`, `attach`, `props`; перечисления принимают имена LVGL, например `LV_TEXT_ALIGN_RIGHT`.

```json
{
  "pressure_warning": {
    "copy": "global:base_text",
    "merge": ["global:large_text", "global:warning_colors"],
    "props": {
      "text_align": "right"
    }
  }
}
```

Предлагаемый фиксированный порядок: исходный `copy`, затем элементы `merge` по порядку массива, затем собственные `props`. Порядок ключей JSON/CBOR-карты не управляет выполнением. `copy` заменяет набор свойств назначения; `merge` добавляет свойства и перекрывает совпадающие; собственные свойства имеют последний приоритет. Все три поля опциональны.

Копирование не создаёт постоянной связи с исходным стилем. Последующие изменения источника сами по себе не меняют ранее составленный стиль. Для повторного получения результата нужна явная пересборка его описания; автоматическое распространение по цепочкам копий не предполагается. Ссылки на внешние ресурсы внутри скопированных значений требуют соблюдения времени жизни самих ресурсов.

На пустом стиле копирование одного источника и слияние одного источника дают одинаковый набор свойств; различие операций важно для уже заполненного назначения. В реализованном v1 команда полностью заменяет результат, поэтому удалённые из описания свойства не сохраняются. Слот держит стабильный адрес `lv_style_t`.

Одновременное подключение нескольких стилей к объекту — отдельный механизм LVGL, не операция `merge`. В первой демке подключён один именованный стиль к MAIN/DEFAULT; области и ограничения ссылок описаны в протоколе. Семантика проверена по [исходникам LVGL 9.6](https://github.com/lvgl/lvgl/blob/v9.6.0/src/misc/lv_style.c) и нативным интеграционным тестом.
