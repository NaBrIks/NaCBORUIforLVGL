# BLE-сканер как пример данных, записей и событий

Опциональный модуль S3-примера использует настоящий пассивный BLE GAP scan и парсер соседнего проекта `ESP32-yabt` (выделен из `ESP32-BLETPMS-and-more/lib/yabt` 2026-10-23). Подключений GATT и сопряжения нет. Код ядра NaCBORUIforLVGL не зависит от ESP-IDF, BLE или yabt.

Приложение регистрирует три заранее известные схемы:

| Источник | Схема | Запись |
|---|---|---|
| `ble.scan.enabled` | Логическое фактическое состояние сканирования | Запрос запуска/остановки через setter приложения |
| `ble.scan.status` | Структура: `state`, `packets`, `dropped`, `count`, `error` | Только чтение |
| `ble.scan.devices` | Массив до 16 структур: `address`, `addressType`, `name`, `rssi`, `manufacturer`, `packets`, `lastSeenMs` | Только чтение |

`manufacturer = -1` означает отсутствие manufacturer ID. RSSI передаётся как значение advertising report; `127` — специальное значение отсутствующего RSSI протокола. `lastSeenMs` — монотонное время получения с загрузки МК. `packets` устройства считает обработанные отчёты этой записи; общий `status.packets` включает все GAP reports, `dropped` показывает повреждённые внешние длины и переполнение очереди. После остановки последние измерения остаются доступны вместе с временем получения; это не доказательство свежего приёма.

Новые адреса не создают новых источников. Запись определяется шестью байтами адреса и его типом. При заполнении таблицы заменяется самая давно полученная запись. Пустое имя нового advertising report не стирает ранее полученное имя. Имена ограничены 32 байтами валидного UTF-8, управляющие/повреждённые байты очищаются. Таблица и её reducer независимы от BLE/LVGL и проверяются отдельным нативным тестом.

Имена и manufacturer ID разбираются только из полных legacy PDU. В ESP-IDF 5.4 extended advertising fragments передаются приложению без сборки; даже последняя часть может иметь статус COMPLETE. Этот минимальный пример не собирает такие payload: для extended PDU сохраняются адрес, RSSI, время и счётчики, но фрагмент не выдаётся за самостоятельный AD-документ. Бит legacy `0x10` подтверждён публичными `ESP_BLE_LEGACY_ADV_TYPE_*`/`ESP_BLE_GAP_SET_EXT_ADV_PROP_LEGACY` и HCI-обработчиком IDF. Неполный/повреждённый внутренний AD-сегмент обрывает разбор yabt по проверке длины без выхода за исходный буфер.

Именованные действия `ble.scan.start`, `ble.scan.stop`, `ble.scan.clear` принимают `null`; выражение редактора — `{literal:null}`. Start/stop и запись `enabled` меняют желаемое состояние; опубликованное `enabled` меняется только после успешного GAP callback. Ошибка остаётся в `status.error`. Clear очищает таблицу и счётчики, сохраняя фактическое состояние сканирования.

GAP callback использует yabt только пока жив исходный буфер и передаёт собственную ограниченную POD-запись в статическую очередь на 32 элемента без ожидания. Полные CBOR/JSON из advertising report не строятся. Приложение обрабатывает очередь в том же UI task, где исполняется LVGL, и публикует снимки не чаще четырёх раз в секунду, кроме изменений управляющего состояния. Общий `DataRegistry::flush()` в цикле применяет данные и отложенные события.

Экран `ble-scanner` состоит из стандартных label, switch и button. На 800×480 одновременно видны восемь строк с общими колонками имени, адреса, RSSI и числа пакетов. Данные доступны для всех 16 записей через общий каталог/API; восемь видимых строк — компоновка примера. Switch показывает подтверждённое состояние и отправляет запись по `value_changed`; Clear вызывает действие по `clicked`. Специальных веток редактора для сканера нет. Экран передаётся через ProjectService: его описание с привязками больше старого 3584-байтного диагностического WS frame.

## Сборка и сохранение авторских экранов

`tools/build_s3.ps1` включает сканер по умолчанию. Adapter компилируется как C++20 из-за `std::span`. Неизменённый внешний `yabt_utils.cpp` требует C++23: в нём есть вспомогательная функция со `std::views::join_with`. Ядро и остальной пример остаются C++17. PlatformIO удаляет только глобальный IDF-флаг `gnu++2b`, сохраняя эти два отдельных флага исходников. `-WithoutScanner` выбирает профиль `s3-no-scanner`; отдельно доступен CMake `LVGL_CBOR_DEMO_BLE_SCANNER=OFF`.

Профиль S3 использует LVGL libc allocator и штатное предпочтение PSRAM для обычного malloc, BT host и WiFi/LwIP. Внутренние DMA-буферы и стеки FreeRTOS остаются внутренними. Порядок запуска: NVS → контроллер/host BLE → дисплей/проект → сеть; фактическое сканирование начинается из UI-цикла после регистрации данных и подтверждения GAP. Это сохраняет непрерывный DMA-блок до остальных аллокаций. FETCH_INSTRUCTIONS, RODATA и PSRAM memtest включены. Размеры образа, реальные перезапуски и ограничения памяти приведены в [аппаратном отчёте](reviews/REVIEW_20261023_bindings-events.md).

Полный сохранённый JSON передаётся явно:

```powershell
./tools/build_s3.ps1 -ProjectJson C:\path\to\preserved-project.json
```

Генератор сохраняет исходные ID, названия, entry, экраны, стили и остальные поля manifest. Он обновляет только две контрольные суммы контрактов для перекомпиляции новым кодеком и добавляет экран сканера, если такого ID ещё нет. Существующий `ble-scanner`, в том числе авторские изменения, сохраняется. База ROM остаётся прежним демонстрационным TPMS/GPS-экраном с явно указанными примерными значениями. Сборка не пишет ни в живой MCU filesystem, ни в переданный JSON.

`examples/s3_style_lab/project/preserved-project.json` — неизменённый авторский экспорт перед этой миграцией: четыре экрана и шесть стилей. Это сохраняемый исходный материал, а не удаляемый результат сборки. Тест сравнивает после подготовки все исходные экраны, их новые скомпилированные пакеты и manifest за исключением двух обновляемых ABI fingerprints.

Низкоуровневая команда: `node tools/project_image.mjs --project-json <file.json> --with-scanner`. Старый `--preserve <file.cbor>` — отдельный режим добавления мастерской с префиксами, его нельзя совмещать с полным `--project-json`. Обновление приложения и filesystem выполняется отдельно, после резервного чтения текущего проекта и проверки платы/разделов.

## Touch и предел проверки

Стандартные зависимости `esp_lcd_touch` 1.2.1 и `esp_lcd_touch_gt911` 1.1.3 соединены с обычным LVGL pointer input. Используются существующие I2C SDA8/SCL9 и последовательность сброса платы; новый драйвер GT911 не написан. `touch_available` сообщает успешную инициализацию, `touch_errors` — ошибки чтения. Эти признаки и программно отправленное LVGL-событие не подтверждают физическое касание панели. Аппаратные результаты указываются отдельно в отчёте проверки.
