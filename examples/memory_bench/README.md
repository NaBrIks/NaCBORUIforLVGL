# Стенд замеров LVGL и NaCBORUIforLVGL

Цель — измерить цену одинакового интерфейса на чистом LVGL и через CBOR,
затем по одному подключать возможности до уровня 7″ демо. В папке лежат общий генератор, профили прошивки,
запуск на S3 и обработка замеров. Ниже также разобрана исходная S3 Style Lab.

[S3 benchmark summary in English](results-s3.md) · [Подробные замеры на S3](results-s3.ru.md).

## Ступени

| Ступень | Что добавляется |
| --- | --- |
| 0. Плата | ESP-IDF, системные задачи и драйвер дисплея. Контрольная точка для платформы. |
| 1A. Прямой LVGL, две сцены | 100 узлов, создаваемых прямыми вызовами LVGL, штатные виджеты и общие медиаресурсы во Flash. |
| 1B. CBOR во Flash, две сцены | Тот же экран из подготовленного на ПК CBOR-массива `const`. LVGL, TinyCBOR и минимальная часть нашего рантайма. |
| 2. Страницы | Основная страница и вложенные экраны. Отдельный замер для освобождения, кэша и удержания. |
| 3. Данные | Реестр, живые значения, обновление индикатора, нажатия и обратные события. История отдельно. |
| 4. Оформление | Именованные стили, несколько ссылок на стили, смена цветовой схемы на ходу. |
| 5. Проекты на FS | ProjectService, монтирование FS, чтение CBOR, сохранение и повторная загрузка проекта. |
| 6. Сеть | Wi-Fi, затем NaWServer, затем HTTP API проекта. Отдельная отметка после каждого запуска. |
| 7. Полный стенд | Встроенный редактор, HTTP/WS предпросмотр, управление, дельты и RLE. Все приборы из штатных виджетов LVGL. |

100 узлов считаются по явным объектам одного видимого дерева. Скрытые
внутренние объекты виджетов LVGL считаются отдельно. Прямой код и CBOR
используют одну раскладку, тексты, шрифты, стили, размеры и один набор
медиаресурсов. Одинаковые фотография и анимированная GIF входят в каждый
профиль с интерфейсом. Ступень 0 оставляет только инфраструктуру платы.
Размеры и лицензии файлов фиксируются вместе с тестовым набором.

В минимальном CBOR-профиле отключены вложенность и биндинги через `LVGL_CBOR_COMPOSITION=OFF` и `LVGL_CBOR_DATA_BINDINGS=OFF`. По умолчанию оба флага ядра включены. Профиль страниц включает композицию, профиль данных добавляет исполнение биндингов и событий. Формат CBOR остаётся ABI v3.

В сравнении 1A/1B держим один target, sdkconfig, формат цвета, число
буферов, конфигурацию LVGL и набор декодеров. Проверяем дерево и отрисовку
на одинаковом кадре анимации. Цена CBOR — разница между двумя реализациями
по Flash, удерживаемой RAM, пику и времени создания. Сравнение с
полной демкой показывает цену полного набора функций.

## Что измерять

- При сборке — файл приложения, секции ELF и вклад архивов и объектов
  по карте линковки. Размер CBOR, фото, GIF, редактора и занятого места FS
  фиксировать отдельно. IRAM, статические данные и heap показывать
  раздельно.
- При запуске — начало `app_main`, после LVGL, после выделения буферов
  дисплея, после построения 100 узлов, после первого flush, после
  первого кадра фото и GIF. Дальше — до и после монтирования FS,
  загрузки проекта, Wi-Fi, NaWServer, подключения клиента и первого
  кадра предпросмотра.
- В каждой отметке — свободно и самый большой свободный блок для
  внутренней RAM и PSRAM. Для нагрузочной операции — локальный минимум
  свободной памяти, время, CPU за одинаковое окно. DMA — отдельная
  характеристика внутренней памяти. Для собственных буферов — фактическое
  число живых байтов и размещение.
- На работающей сцене — смена и закрытие страницы, смена схемы,
  переподключение клиента, RAW/RLE, HTTP/WS и возврат памяти после
  закрытия. Первые выделения декодеров измерять отдельно от следующих
  циклов. Полноэкранные и частичные буферы сравнивать отдельным опытом.

На первой серии достаточно счётчиков ESP-IDF и точечных замеров в
прикладном коде, как в NaWServer Compact. Диагностику выдавать в UART,
чтобы измерения минимальных вариантов не требовали Wi-Fi и сервера.
После стабилизации сравнивать повторные старты и показывать разброс.
Хостовые симуляции проверяют совпадение UI. Расход памяти МК снимается
на самом МК.

## Сборка и прогон

Обе контрольные сцены имеют по 100 объявленных узлов. Повторяющаяся сцена
содержит восемь одинаковых групп. Прямой код строит их двумя вложенными
циклами. В разнородной сцене по группам меняются типы, параметры и
состояния. Прямые вызовы LVGL генерируются из того же дерева, что и CBOR.
Оба минимальных профиля с прямыми вызовами не линкуют NaCBORUIforLVGL.
В CBOR-сценах штатный GIF LVGL доступен через регистрацию фабрики
`bench:gif`. Фабрика вызывает `lv_gif_create`, обработка GIF остаётся в LVGL.

Одинаковые тестовые ресурсы находятся в `assets/`. Портрет взрослой женщины сгенерирован и преобразован на ПК
в нативный RGB565 LVGL, 192 × 192, 73 728 Б. На МК он читается напрямую
из Flash через `lv_image_dsc_t`. GIF — оригинальная анимация
робота, 192 × 128, 22 кадра по 100 мс, 14 317 Б.

```powershell
npm ci
./examples/memory_bench/build.ps1
./examples/memory_bench/build.ps1 -Profiles direct-repeat,cbor-repeat,direct-mixed,cbor-mixed
python ./examples/memory_bench/report.py
```

Прошивку и трассы хранит игнорируемый `out/<profile>/`. Для аппаратного
прогона нужен Python с pyserial, например окружение PlatformIO, и
esptool. Список параметров выдаёт `python examples/memory_bench/measure.py --help`.
Сценарий сверяет USB-серийный номер и таблицу разделов, сохраняет
активный app-раздел (factory или выбранный OTA), записывает только app и восстанавливает его
после серии. Проектный раздел используется лишь начиная с FS-ступени.
Стенд монтирует его без форматирования и пишет отдельные файлы
`bench-layout-v1.cbor` и `bench-changes-v1.*`. Сетевые сборки читают
игнорируемый `wifi_secret.hpp` существующей демки. Их образы не следует
публиковать.

Метки собираются в зарезервированном стеке главной задачи и выводятся
после первого окна анимации. `ram_min` и `psram_min` для этапов с
локальным мониторингом относятся к интервалу операции. Время `us`
отсчитывается от запуска таймера ESP-IDF. Чтобы оставить последний
проверенный профиль на экране, добавьте `--leave-last`. Параметры фаз и необработанные
сэмплы остаются в `out`. Хеш первого RGB565-кадра вычисляется по
равномерной выборке пикселей с остановленной GIF.

## Цена форматирования чисел

Числовая подпись биндинга и JSON-адаптер используют общий форматтер.
На S3 измерены `std::ostringstream`, `std::to_chars` и `std::snprintf`
с прикладными потоками C++ и без них. Для ESP-IDF по умолчанию выбран
`snprintf`. [Результаты, график и параметры сборки](number-format-s3.md).

## Разбор прежних 91,9 КиБ

В полном образе S3 Style Lab сумма `.dram0.data` и `.dram0.bss` составляет
**94 156 Б**. Это статические данные всего приложения. Данные дисплея
в PSRAM, выделения LVGL/SDK и стеки задач, созданных через heap, в эту
сумму не входят. Карта линковки также содержит **107 807 Б** в
`.iram0.text` и `.iram0.vectors`, это отдельные секции кода и векторов.

Две очереди вместе с текущими пакетами занимают **28 716 Б**. Буфер

не учитывается. Для поиска причины расхода сначала измеряем владельцев
в минимальных профилях и только затем оцениваем, можно ли менять глубину
очередей или выделять память при подключении.
